MIDI

Overview

Q reads MIDI as typed messages. A message on the wire, three bytes of MIDI 1.0 or a packet of MIDI 2.0, becomes a small value type with accessors, a note_on with its key() and velocity(), and is handed to a processor: a class with one function call operator for each message it handles. Everything in the MIDI part of the library is built around that one shape, and none of it depends on a device or an operating system. q_io supplies the device end; a plugin host or a file may supply it instead.

Figure 1. Bytes or packets come in on the left and typed messages reach a processor on the right. A chain is written for one protocol, and takes the other through a translator.

Both protocols are covered, each in its own namespace. MIDI 1.0 is the protocol of five-pin cables and of most instruments in use: a status byte and up to two data bytes of 7 bits each. MIDI 2.0 is its superset: the same messages at 16 and 32 bits, new ones that address a single note of a chord, all carried in Universal MIDI Packets of one to four 32 bit words. A packet stream can carry MIDI 1.0 messages too, so the two meet in one place.

Endpoints and Devices

A processor can be either a device or an endpoint, or both.

An endpoint is where a UMP connection terminates. It has a name, a serial number, a manufacturer and model, the protocols it takes, and a topology: a list of function blocks, each a named set of groups with a direction. Anything at the end of a packet connection is one, whichever way the notes flow.

A device is something with a MUID that implements MIDI Capability Inquiry: discovery, profiles, property exchange. On a packet connection a MUID belongs to a function block, not to the endpoint, so an endpoint with three MIDI-CI capable blocks holds three devices.

Neither implies the other, and all four combinations exist:

  • A USB pad controller that only sends notes. An endpoint, not a device. A host learns its name and its one function block from the stream messages, and nothing in system exclusive replies: Function Block Info declares a MIDI-CI version of 0x00 for none.

  • A virtual synth that makes sound and nothing else. An endpoint, not a device. The common case.

  • A keyboard workstation with profiles and a patch list. Both. Its keyboard, its pads and its control surface are three function blocks, each with its own MUID, so a host configures one without touching the others.

  • A guitar controller with a string per group. Both: one connection with one name, six function blocks, six MUIDs, so a profile goes on for one string alone.

  • An instrument on a five-pin cable that implements MIDI-CI. A device, not an endpoint. That shipped in 2020, before there was any UMP hardware, and it runs over ordinary system exclusive, so there is a MUID and no groups, no function blocks and no endpoint.

  • A plugin that serves its patch list through the host’s system exclusive routing. A device, not an endpoint.

  • A plugin that only makes sound. Neither.

A plugin is neither a device nor an endpoint by default. It becomes a device by implementing MIDI-CI, and an endpoint by opening a port of its own.

A plugin receives MIDI through the host’s port; the port is the endpoint, and the plugin is a device.

What follows from that is how Q is put together. endpoint_description and stream_responder are the endpoint, one per connection, and they are built on the packet reader. midi_ci::responder is the device, one per MUID, and it is built on sysex_view, which either reader produces. The same MIDI-CI code serves a device on a five-pin cable and a function block inside an endpoint, without knowing which.

Declaring a Role

A class says which of the two it is by having the member for it:

struct my_instrument : midi2::processor
{
   using midi2::processor::operator();
   void operator()(midi2::note_on msg, std::size_t time);

   midi2::endpoint_description&  endpoint();        // the endpoint role
   ci::device_description const& device() const;    // the device role
};
midi2::stream_responder stream{my_instrument, send, my_instrument};
ci::responder           ci{my_instrument, rng};

A responder takes the description it needs, so one class can be the synth, the endpoint and the device at once, which for a simple instrument is the natural thing to write. A class that is only a synth has neither member and is passed as the processor alone. A caller with no such class hands a description over directly instead, as before.

endpoint() returns a non-const reference because a granted Stream Configuration Request changes the protocol in use, and the endpoint reports the state that now holds. The class keeps that field, and the change shows there.

The device’s property and profile hooks in MIDI Capability Inquiry fit the same way, so a class that plays the device role can serve property inquiries with members beside these.

Namespaces

namespace cycfi::q::midi     { /**...**/ }   // what both protocols share
namespace cycfi::q::midi_1_0 { /**...**/ }   // MIDI 1.0
namespace cycfi::q::midi_2_0 { /**...**/ }   // MIDI 2.0 and the packet
namespace cycfi::q::midi_ci  { /**...**/ }   // MIDI Capability Inquiry

midi holds what both protocols share: message_base, which every message derives from; the default no-op processor; the controller names in cc; the note helpers; the per-note messages note_pitch, note_pressure and note_timbre; and the Processor concept, in concepts::midi. The system messages and sysex_view are named there as well, since MIDI 2.0 carries them unchanged. Each protocol’s namespace names what it uses of these, so midi_1_0::cc and midi_2_0::cc are both midi::cc.

The Layers

The wire

A reader makes whole messages from incoming data. See MIDI Readers. byte_reader takes MIDI 1.0 bytes, keeps running status, and gathers a system exclusive message until it ends. packet_reader takes packets and gathers what spans several of them: system exclusive in its 7 bit and 8 bit forms, and the stream messages that carry text. A message too long for a reader’s buffer is dropped whole, never truncated.

Dispatch

dispatch turns one raw message or one packet into the type it holds and calls the processor with it. See MIDI 1.0 Messages, MIDI 2.0 Messages and MIDI Processor. The MIDI 2.0 dispatch hands the MIDI 1.0 voice messages and the system messages a packet may carry to the MIDI 1.0 dispatch, so a MIDI 2.0 processor receives those as the MIDI 1.0 types they are.

The stages

A stage reads meaning out of messages. See MIDI Stages. It is a processor proxy: it handles the messages it reads and forwards the rest inward. parameter_reader assembles the six controllers that spell a registered or unregistered parameter. cc14_reader joins the coarse and fine halves of a 14 bit controller. mode_reader turns controllers 120 and up into the channel mode messages they are. mpe_reader reads a zone’s channels as messages about single notes, and per_note_reader reads MIDI 2.0’s per-note messages as the same three: note_pitch, note_pressure and note_timbre.

Between the protocols

to_midi1 and to_midi2 are stages too. See MIDI Translation. One narrows MIDI 2.0 messages to MIDI 1.0 and drops what MIDI 1.0 cannot say; the other widens MIDI 1.0 messages to MIDI 2.0. A processor written for either protocol can therefore be fed by either kind of stream. The resolution scaling they use keeps zero, the maximum and the center of a bipolar value exact.

The endpoint

Before a host sends a note it asks the device what it is: its name and serial number, its manufacturer, family and model, the protocol it takes, and the function blocks it is made of. See MIDI Endpoint. The stream messages carry that conversation, stream_responder replies from a description the device supplies, endpoint_inquiry sends them and gathers the replies, and MIDI Capability Inquiry runs a second conversation over universal system exclusive. See MIDI Capability Inquiry.

Chaining

Dispatch is called once, at the front, and stages nest in one expression:

namespace midi = cycfi::q::midi_1_0;

auto chain = midi::parameter_reader{midi::cc14_reader{my_synth}};
midi::dispatch(msg, time, chain);

Here my_synth is a processor, cc14_reader wraps it, and parameter_reader wraps that. A message goes to the outermost stage first.

Order matters where two stages read the same controllers. See MIDI Stages.

What Q Does Not Do

Every message type either MIDI protocol defines now reaches an overload, so nothing arrives that Q cannot name. What follows is what Q leaves to the application, and why in each case.

It Keeps No Clock

Nothing in q_lib times anything out. MIDI-CI gives a responder three seconds to reply and asks for a jitter reduction clock every 250 milliseconds, and Q reads both and acts on neither.

This is the same decision that makes a 14 bit controller report its coarse half at once rather than waiting for the fine one. A library that may run in an audio callback has no clock of its own, and inventing one would put a timer where a caller already has a better one. So endpoint_inquiry takes the time it was asked at and hands it back, and the caller decides when to give up. See MIDI Endpoint.

It Asks the Device What Only the Device Knows

Q handles these, and the device supplies the part it alone can:

  • A ResourceList is the one property document the Common Rules make mandatory, and what is in it is a list of what this particular device has. Q requests it from the device.

  • A property subscription is a request to be told when something changes. Q replies to the start and the end and sends the updates. The device holds the table of who subscribed to what, and decides both that something changed and how much of it to send.

  • A profile is turned on and off by Q, from the list the device declares. But only the device knows when it has gained or lost one, so no responder sends a Profile Added or Profile Removed report by itself.

One inquiry Q does not handle at all. A MIDI Message Report asks a device to play back every controller value and every note it is holding. The reply is a stream of MIDI the device must produce, so a device that declares the capability handles the message itself and one that does not gets a NAK.

It Sends Less Than It Reads

  • set_chord_name has no field constructor. A constructor with fourteen arguments, two chords with six alterations between them, would be unusable, and a builder waits on a better design. Reading one is implemented. See MIDI 2.0 Messages.

  • The MIDI-CI initiators send ASCII only. Property data goes out in ASCII, with Mcoded7 and zlib left for later, and a Set’s chunks go one after the other without per-chunk flow control. See MIDI Capability Inquiry.

Deliberate Absences

  • Protocol Negotiation, MIDI-CI category 1, is omitted. Version 1.2 deprecated it, and the Stream Configuration Request in MIDI Endpoint replaced it.

  • The zlib property encoding is absent. It would put a compression library into a header-only audio library for the sake of one message type. Mcoded7 is implemented; it is bit packing.

  • Property pagination has its header keys named and no more, since paging a document is the device’s own affair.

  • Has Property Data, sub-IDs 0x32 and 0x33, is reserved by the specification itself and has no defined layout to implement.

  • The property notify message has its builder and is otherwise absent, since the acknowledgement and the refusal have taken its place.

  • Profile added and removed reports, and profile specific data, can be built and read, but no responder sends them on its own, because only the device knows when it has gained or lost a profile.

Not Gathered, on Purpose

A mixed data set can carry a firmware image. packet_reader hands each packet over as it arrives; a buffer large enough to assemble one does not belong inside a reader. A system exclusive is assembled, because it is bounded and small. See MIDI Readers.
