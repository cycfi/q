Tasks

Overview

Tasks are work posted from one thread, the poster, to be run on another, the owner, real-time safe at both ends: neither thread takes a lock or waits, and nothing is allocated after construction, so either may be a real-time thread. The owner runs what is due at its own tick, once per cycle: the top of each audio block, a timer on the main thread. A task runs at the owner’s next tick, or after a delay. Tasks are implemented by a class template named basic_tasks, and tasks is the one for wall time.

It is the post-and-poll pattern of an event loop, as in asio’s io_context and Elements' view::post, made real-time safe. A main thread can post a change for the audio thread to make at the top of its next block. An audio thread can post a report for the main thread to act on at its next tick, where it may allocate, lock or draw.

Figure 1. Tasks: posted on the poster thread, and run on the owner thread.

  • post hands a task over, on the poster thread.

  • poll runs the tasks that are due, on the owner thread, and frees the space they took for later posts.

Tasks run in the order they were posted, and each one runs once. poll runs only the tasks waiting when it starts, so a burst of posts while it runs cannot lengthen it.

For an object that needs allocation, such as a sample buffer, where only the latest one matters, use a handoff instead.

What a Task Can Hold

A task is any callable that is trivially copyable and trivially destructible: a lambda that captures this, pointers and plain values, of any size. Copying such a task in, and dropping it after it runs, can never allocate or free memory, on either thread. A callable that owns memory, one that captures a std::string, a std::shared_ptr or a std::function, does not compile.

The tasks share the space given when the tasks is made, each taking what it needs. post returns false when a task does not fit in the space left, and the task is not posted.

Delays and Clocks

A task posted with a delay runs at the first poll at or after its due time: the time of the post plus the delay, on the clock. The clock is the template parameter, and the right one depends on whose time the delay is in:

  • Wall time, for an owner that keeps time with the world: a tooltip’s delay on the main thread. This is tasks, on the system’s steady clock.

  • Audio time, for delays measured in the audio itself. An audio_clock counts the frames the audio thread has processed. It stands still while no audio is processed, and in an offline render it runs as fast as the render does, so 500 ms is 500 ms of audio.

The clock can be held by reference, basic_tasks<audio_clock&>, so the audio thread advances one clock that the tasks read.

A task can run late by up to one of the owner’s cycles, since it runs at a poll, never between two. Tasks that come due at the same poll run in the order they were posted.

A delayed task never holds back the tasks posted after it. next_due gives the earliest due time among the delayed tasks poll has seen: a poster that owns the clock, as an audio thread owns its audio_clock, can compare it with the time now and wake the owner just when something comes due.

Include

#include <q/utility/tasks.hpp>

Declaration

namespace concepts
{
   template <typename C>
   concept Clock = requires(C const& c, duration d)
   {
      { c.now() } -> std::same_as<std::int64_t>;      // the time now
      { c.ticks(d) } -> std::same_as<std::int64_t>;   // d, in the same ticks
   };
}

template <typename Clock>
requires concepts::Clock<std::remove_reference_t<Clock>>
class basic_tasks
{
public:

   explicit          basic_tasks(std::size_t bytes);
                     basic_tasks(Clock clock, std::size_t bytes);

   // Poster thread.
                     template <typename F>
   bool              post(F&& f);

                     template <typename F>
   bool              post(duration delay, F&& f);

   // Owner thread.
   void              poll();

   // Any thread.
   std::int64_t      next_due() const;
};

using tasks = basic_tasks<_steady_clock_>;   // the system's steady clock, in ns

post accepts F only if std::decay_t<F> is invocable with no arguments, trivially copyable and trivially destructible. A clock’s now and ticks may be called from any thread.

Call post from one poster thread, and poll from one owner thread. A task runs on the owner thread, so whatever it touches must be safe to touch there. next_due counts only the tasks a poll has seen.

Example

A synth’s volume is set from the main thread. The change is posted as a task, and the audio thread makes it at the top of its next block, so the voice never reads a half-written value. A second change, posted with a delay on the audio thread’s own clock, fades back up two seconds of audio later:

#include <q/utility/tasks.hpp>
#include <q/utility/audio_clock.hpp>
#include <q/support/literals.hpp>
#include <q_io/audio_stream.hpp>   // For audio_stream

namespace q = cycfi::q;
using namespace q::literals;

struct synth : q::audio_stream
{
   synth()
    : audio_stream(0, 1)
   {}

   void process(out_channels const& out) override
   {
      tasks.poll();                                               (1)
      for (auto frame : out.frames)
      {
         _phase = _phase < 1.0f? _phase + 0.01f : -1.0f;          // a saw
         out[0][frame] = _phase * _volume;
      }
      clock.advance(out.frames.size());                           (2)
   }

   void duck(float v)
   {
      tasks.post([this, v] { _volume = v; });                     (3)
      tasks.post(2_s, [this] { _volume = 1.0f; });                (4)
   }

   q::audio_clock clock{48000};
   q::basic_tasks<q::audio_clock&> tasks{clock, 1024};            (5)
   float _volume = 1.0f;
   float _phase = 0.0f;
};

...

synth s;
s.start();
s.duck(0.5f);                                                     (6)
1 Run the tasks that are due, at the top of the block, on the audio thread.
2 Move the audio clock on by the frames just processed.
3 Post the change. The lambda captures this and a float, so it is trivially copyable.
4 And the change back, two seconds of audio from now.
5 Tasks timed on the synth’s clock, with 1 KB for tasks waiting.
6 Called on the main thread. The volume halves at the start of the next block, and comes back after two seconds of audio.

See Audio Stream Client Interface for more info on process.

Implementation Details

Implementation details are subject to change without notice. Rely only on the expressions above.
Figure 2. Inside tasks: posted on the poster thread, held in a ring allocator, and run on the owner thread.

  • Blue carries the tasks: post copies each one into a ring_allocator, behind a small header that holds its run function and its due time, and poll runs them on the owner thread.

  • Green frees their space: once poll has run the tasks waiting, their space is free for later posts.

poll runs the tasks that are due and moves the rest, as bytes, to the back of a second ring allocator that only the owner touches. A trivially copyable task can be moved that way. The second ring has twice the space, so moving its tasks along always has room while they fill half of it. Beyond that, a task that cannot move stays where it is, and post fails once the first ring fills, so nothing is lost. Tasks that come due at the same poll run in the order posted, unless a ring stopped early.
