MIDI Translation

Overview

Read MIDI 1.0 Messages and MIDI 2.0 Messages first for prerequisite information.

A processor is written for one protocol, and streams come in both. to_midi1 and to_midi2 stand between them. Each is a processor proxy: to_midi1 takes MIDI 2.0 messages and hands the processor behind it MIDI 1.0 ones, and to_midi2 does the reverse. A processor written for either protocol can therefore be fed by either kind of stream.

Figure 1. A translator stands between the stream and the processor, so a processor written for one protocol can be fed by either kind of stream.

  • The processor behind to_midi1 is written for MIDI 1.0, and the one behind to_midi2 for MIDI 2.0.

MIDI 2.0 is the superset, so the two directions are not alike. Widening loses nothing: every MIDI 1.0 message has a MIDI 2.0 form, and the value is scaled up so that zero, the maximum and the center of a wheel stay exact. Narrowing is best effort: a value loses resolution, and a message MIDI 1.0 has no form for, per-note pitch bend among them, is dropped.

Both follow the Default Translation Mode of the MIDI 2.0 specification (M2-104-UM, Appendix D), with values scaled as its companion on bit scaling says (M2-115-U). See MIDI for where translation sits among the readers and stages.

Use Case

A synth written for MIDI 1.0 two years ago, in a host that now sends packets. to_midi1 in front of it narrows each packet to the message the synth already handles. Nothing in the synth changes.

my_midi1_synth synth;
midi2::packet_reader<> reader;
auto chain = midi2::to_midi1{synth};
void on_packet(midi2::packet const& packet, std::size_t time)
{
   reader(packet, time, chain);
}

Include

#include <q/midi/translate.hpp>    // to_midi1, to_midi2
#include <q/midi/scaling.hpp>      // the scaling functions

Declaration

namespace cycfi::q::midi_2_0
{
   template <typename P>
   class to_midi1
   {
   public:

      explicit                to_midi1(P next);

                              template <typename Message>
      void                    operator()(Message msg, std::size_t time);
   };

   template <typename P>
   class to_midi2
   {
   public:

      explicit                to_midi2(P next);

                              template <typename Message>
      void                    operator()(Message msg, std::size_t time);
   };

   constexpr std::uint32_t scale_up(
      std::uint32_t value, unsigned from_bits, unsigned to_bits);
   constexpr std::uint32_t scale_down(
      std::uint32_t value, unsigned from_bits, unsigned to_bits);

   constexpr std::uint32_t zero_extend_up(
      std::uint32_t value, unsigned from_bits, unsigned to_bits);
   constexpr std::uint32_t zero_extend_down(
      std::uint32_t value, unsigned from_bits, unsigned to_bits);

   constexpr bool registered_uses_zero_extension(std::uint8_t index);
}

Both translators take every message. Those of the protocol they translate from are translated; everything else passes through to the processor behind it unchanged, the system messages and system exclusive included.

Using the Translators

A translator goes between dispatch, on MIDI Processor, and the processor, like any other stage:

namespace midi = cycfi::q::midi_1_0;
namespace midi2 = cycfi::q::midi_2_0;

// A MIDI 1.0 synth, fed by a packet stream
auto chain = midi2::to_midi1{my_midi1_synth};
midi2::dispatch(packet, time, chain);

// A MIDI 2.0 synth, fed by MIDI 1.0 messages
auto chain = midi2::to_midi2{my_midi2_synth};
midi::dispatch(raw, time, chain);

to_midi2 is kept between calls, not made afresh for each message: it holds the halves of a parameter and a bank select until they are complete.

Translation substitutes rather than adds. Behind to_midi1 a MIDI 2.0 note_on becomes a MIDI 1.0 note_on and the original is not delivered, so a midi_2_0::note_on overload written alongside is never called. The reverse holds behind to_midi2.
Figure 2. What reaches the processor is the MIDI 1.0 note_on, not the MIDI 2.0 one that produced it.

  • The note_on on the left is MIDI 2.0. The one to_midi1 hands on is MIDI 1.0.

  • The processor is written for MIDI 1.0.

MIDI 1.0 to MIDI 2.0

to_midi2 widens, as Appendix D.3 says:

MIDI 1.0 message Arrives as

note_on

note_on, velocity from 7 bits to 16. One of velocity 0 arrives as a note_off: MIDI 1.0 means a note-off by it, and MIDI 2.0 can say so.

note_off

note_off, velocity from 7 bits to 16.

poly_pressure

poly_pressure, from 7 bits to 32.

control_change

control_change of the same number, from 7 bits to 32, for every controller but the eight below.

control_change 101 and 100, then 6 and 38

One registered_controller, its value from 14 bits to 32. Three things send it, whichever comes first: controller 38 arrives, a second controller 6 arrives, or a new parameter is selected. A fine half that never arrives counts as zero.

control_change 99 and 98, then 6 and 38

One assignable_controller, the same way.

control_change 0 and 32

Nothing of their own. The bank waits for the next program_change and rides along with it.

program_change

program_change, with the bank when one was selected.

channel_pressure

channel_pressure, from 7 bits to 32.

pitch_bend

pitch_bend, from 14 bits to 32.
Figure 3. The four controllers of a registered parameter go in and one message comes out. Nothing is sent until controller 38 completes the value.

  • to_midi2 holds the parts, and nothing is sent for the first three.

  • Controller 38 completes the value, and the registered_controller goes out, widened to 32 bits.

  • A second controller 6, or a new selection, sends it too.

Translated messages are addressed to group 0, since a MIDI 1.0 stream has no groups to carry over.

The null function, both select halves set to 0x7F, selects nothing and is not translated.
The specification suggests one more, a short timeout after a controller 6, for a sender that never sends 38 and then goes quiet. Q does not do this. Nothing in q_lib holds a clock, and the three above already cover a sender that keeps sending.

MIDI 2.0 to MIDI 1.0

to_midi1 narrows, as Appendix D.2 says:

MIDI 2.0 message Arrives as

note_on

note_on, velocity from 16 bits to 7. One that scales to 0 arrives as 1, since 0 would read as a note-off.

note_off

note_off, velocity from 16 bits to 7.

poly_pressure

poly_pressure, from 32 bits to 7.

control_change

control_change, from 32 bits to 7.

registered_controller

Four control_change messages: controllers 101 and 100 select the parameter, 6 and 38 carry its value in 14 bits.

assignable_controller

The same, with controllers 99 and 98.

program_change

program_change, after the bank select controllers 0 and 32 when the message carries a bank.

channel_pressure

channel_pressure, from 32 bits to 7.

pitch_bend

pitch_bend, from 32 bits to 14.

relative_registered_controller, relative_assignable_controller, registered_per_note_controller, assignable_per_note_controller, per_note_management, per_note_pitch_bend

Nothing. MIDI 1.0 has no form for them.
What a MIDI 1.0 synth loses this way it can have back through Per-Note Expression, which reads MIDI 2.0’s per-note messages, ahead of to_midi1, as the same note_pitch, note_pressure and note_timbre that MPE gives.

Scaling

MIDI 1.0 holds 7 bits, or 14 for a bend; MIDI 2.0 holds 16 for a velocity and 32 for everything else. Moving a value between them takes more than a shift, because three points must land exactly: silence on silence, full on full, and the center of a wheel on the center. A plain shift gets two of the three and stops short of the maximum: 127 becomes 65024, not 65535.

Figure 4. Scaling 7 bits to 16. Both agree up to the center. Above it, Min-Center-Max stretches the upper half so that 127 reaches 65535.

Two schemes cover it:

Min-Center-Max

scale_up and scale_down, for controllers and anything continuous. Going up, a value at or below the center is shifted; above the center, the vacated low bits are filled by repeating the value’s own bits, which stretches the upper half so the maximum reaches the maximum. Going down is a plain shift, and recovers the original.

Zero extension

zero_extend_up and zero_extend_down, for a registered controller whose index is 0 to 31. Those are the MIDI 1.0 registered parameters, counts and settings such as pitch bend sensitivity, a number of semitones, and a count must not be stretched. Going up is a shift, so 127 becomes 65024. Going down is a shift with rounding, clamped.

registered_uses_zero_extension says which a registered controller takes. The translators use these functions; they are also there for code that scales a value itself.

scale_up(127, 7, 16);             // 65535
scale_up(64, 7, 16);              // 32768, the center
scale_up(8192, 14, 32);           // 0x80000000, the center of a bend
scale_down(0xFFFF, 16, 7);        // 127
zero_extend_up(127, 7, 16);       // 65024
