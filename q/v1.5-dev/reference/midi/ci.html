MIDI Capability Inquiry

Overview

Read MIDI Readers first for prerequisite information.

MIDI Capability Inquiry, MIDI-CI, is how two devices find out what each other can do. It is older than the Universal MIDI Packet and independent of it: the messages are universal system exclusive, they run over MIDI 1.0 as readily as over MIDI 2.0, and a device is identified by a MUID rather than by a connection. Where MIDI Endpoint covers what a UMP connection is, this page covers what the device at the other end can do.

Everything here is in namespace midi_ci. Q covers three of the specification’s categories: discovery, profile configuration and property exchange. The last section of this page says what is left out and why.

Use Case

A DAW asks a synth what it can offer. Through property exchange it requests ResourceList, learns the synth has a ProgramList, requests that, and shows the user "Warm Pad" and "Brass" where it would otherwise show program numbers. The synth supplies two JSON documents and nothing else; the responder handles the rest.

struct my_device
{
   std::string_view property(std::string_view resource)
   {
      if (resource == ci::resource_list)
         return R"([{"resource":"ProgramList"}])";
      if (resource == "ProgramList")
         return R"([{"title":"Warm Pad","bankPC":[0,0,1]},{"title":"Brass","bankPC":[0,0,2]}])";
      return {};                                 // anything else is a 404
   }
};

Include

#include <q/midi/ci.hpp>                 // discovery, the headers, the replies
#include <q/midi/profiles.hpp>           // profile configuration
#include <q/midi/property_exchange.hpp>  // property exchange

What a Device Writes

A device builds one chain of responders and feeds it every system exclusive message a reader hands over. Each responder handles the messages of its own category and passes the rest along, and the discovery responder at the end sends a NAK for anything no responder claimed.

Figure 1. One chain. Each responder takes the messages of its category and passes the rest to the next, and the last refuses what nothing claimed.

  • The sysex_view comes from a reader.

  • property_responder handles property exchange: Get, Set and subscriptions.

  • profile_responder handles profiles: inquiry, on and off.

  • responder handles Discovery and Invalidate MUID, and sends a NAK for the rest.

  • Every reply goes out through send.

namespace midi = cycfi::q::midi_1_0;
namespace ci = cycfi::q::midi_ci;

// 1. The discovery responder, innermost. rng() gives a std::uint32_t.
ci::responder discovery{identity, rng};

// 2. Profiles and properties in front of it, in either order.
ci::profile_responder profiles{my_profiles, discovery};
ci::property_responder properties{my_device, profiles};

// 3. Every system exclusive message goes to the outermost.
void operator()(midi::sysex_view msg, std::size_t time)
{
   properties(msg, send);        // send(byte_span)
}

What my_profiles and my_device are is the subject of the two sections that follow. A device with no profiles leaves that responder out, and one with no properties leaves that one out. The discovery responder alone is a complete MIDI-CI device, one that identifies itself and refuses everything else.

Do not call the MUID generator random. POSIX declares a function of that name, so an unqualified random in the global namespace is ambiguous and will not compile.

Discovery

Every MIDI-CI exchange begins the same way: a device sends a Discovery message to the broadcast address, and every MIDI-CI device that receives it replies with its own. Each device is known by a MUID, a 28 bit random number it generates at power on. Profiles, property exchange and process inquiry are further exchanges built on discovery, each with a responder of its own below. A message for a category a device does not support is met with a NAK.

Figure 2. Discovery, then the two inquiries a responder handles on its own. Anything else addressed to it is refused.

responder is the device’s side of discovery. It takes the sysex_view a reader hands over, from either protocol, and sends its replies as whole system exclusive messages, 0xF0 to 0xF7. send is a Sink over byte_span, or a callable taking one, and every responder on this page takes it the same way.

It receives It does

A Discovery, addressed to it or to everyone

Sends a Reply to Discovery with its identity.

A message from a device that has its MUID

Resolves the collision, as the specification’s option B says.

An Invalidate MUID naming its own

Takes a new MUID.

Any other MIDI-CI message addressed to it

Sends a NAK.

Anything else

Nothing.

random is called for a new MUID, at construction and whenever the current one is invalidated. The specification requires a good generator, and a device must not reuse a MUID across restarts. Values that are reserved, or the broadcast address, are drawn again.

The views a device reads a message through, message_view, discovery_view, discovery_reply_view, invalidate_muid_view and nak_view, each check that they are looking at the message they name and that the bytes they read are there, with valid(). The builders make_discovery_reply, make_invalidate_muid and make_nak each write a whole message into a buffer of max_message bytes and return its length.

Initiator

A host opens a port and wants to know which MIDI-CI devices are on it: a synth, a controller, a second copy of itself. initiator asks, gathers the answers into a table, and keeps the table current as devices come and go.

namespace cycfi::q::midi_ci
{
   struct remote_device
   {
      constexpr bool    supports(std::uint8_t c) const;  // a category::* bit

      std::uint32_t     muid;
      midi_ci::identity identity;
      std::uint8_t      categories;
      std::uint32_t     max_sysex_size;
      std::uint8_t      output_path;
      std::uint8_t      function_block;   // 0x7F when not known
   };

   constexpr std::size_t default_reply_window = 3'000'000'000;  // 3 s in ns

   template <typename Next, std::size_t MaxDevices = 16>
   class initiator
   {
   public:
      using device_list = std::span<remote_device const>;

      explicit                initiator(
                                 Next next
                               , std::size_t reply_window
                                    = default_reply_window);

                              template <typename Send>
      void                    poll(Send&& send, std::size_t time);

                              template <typename Send>
      void                    operator()(
                                 midi_1_0::sysex_view msg, Send&& send);

      device_list             devices() const;
      std::size_t             dropped() const;
      bool                    started() const;
      bool                    complete() const;
      void                    restart();

      std::uint32_t           muid() const;
                              template <typename Send>
      void                    announce(Send&& send);
   };
}

A device has one MUID, whether it asks or answers, so the initiator sits in front of the responder chain and uses that chain’s MUID. Next is the chain: a responder, or the profile and property responders built on one, all of which provide muid() and announce(send). The Discovery the initiator sends is the same one announce sends.

ci::initiator inquiry{properties};       // in front of the whole chain
inquiry.poll(send, now);                 // sends Discovery when a round starts
inquiry(sysex, send);                    // every MIDI-CI message goes through here
for (auto const& d : inquiry.devices())
   show(d.muid, d.identity);
It receives It does

A Reply to Discovery addressed to it

Adds the device that sent it, or refreshes it.

A Discovery from another device

Adds that device, and passes the message on so the responder replies.

An Invalidate MUID naming a device in the table

Removes it, and passes the message on.

A Reply to Discovery from a device that has its MUID

Invalidates the MUID and passes that on: the responder takes a new one and asks again from it.

A second Reply to Discovery from one MUID in a round

Two devices share that MUID (5.9.2): invalidates it, passes that on, and removes the device.

Anything else

Passes it on.

Q has no clock, so the caller passes the time to poll, in whatever unit it uses; the default reply window is three seconds in nanoseconds, the unit q_io timestamps are in. The first poll sends the Discovery and starts a round. When the window has passed, a device that did not reply in it is removed and complete() turns true. restart() begins another round, which is how a host notices a device that has gone quiet.

If Next has device_added(remote_device const&) or device_removed(std::uint32_t muid), the initiator calls them as the table changes. The table holds MaxDevices entries, and dropped() counts the devices there was no room for.

supports(c) is true when the device declared category c (category::profiles, property_exchange or process_inquiry) in its reply. MIDI-CI does not forbid asking a device outside its categories, and the device answers such a request with a NAK (5.5.2, 5.11), so the initiators send what they are given; an application that asks only for what a device declares checks supports first.

What MIDI-CI Version 1.2 Added

Q implements version 1.2 of MIDI Capability Inquiry, and three things in it are newer than discovery.

Endpoint Information, section 5.8, requests the product instance id. That id distinguishes a device’s own message echoed back to it from a genuine collision with another device of the same model, since the two share an identity but not an id. A responder replies with the id it was given, capped at the sixteen bytes the specification allows.

The acknowledgement, section 5.10, has the same fields as the NAK and the opposite meaning. Both were given their fields in version 1.2, so a version 1.1 NAK is the header and nothing else, and nak_view reads either.

Process inquiry, section 9, requests the state a device is holding: which controllers are where, which notes are on. A device first reports which of these it can do, and a MIDI Message Report then requests them by three bitmaps, with a control byte selecting everything or only what is not at its default.

Each writes one whole message into out and returns its length.

A responder handles the two inquiries whose reply is simply what the device is, Endpoint Information and Process Inquiry Capabilities. It does not handle a MIDI Message Report, because that reply is every controller and note the device is holding and only the application knows those. A device that claims the feature handles that one itself, and the responder stays silent on it; a device that does not claim it gets a NAK.

Profile Configuration

A profile is an agreement about what a device does with the messages it already understands. A drawbar organ profile defines which controller is which drawbar, so a control surface can drive an organ it has never met. Q covers category 2 of MIDI-CI, from section 7 of the MIDI-CI specification and the Common Rules for MIDI-CI Profiles.

A device declares what it has, and the responder replies from that list:

Declaration

namespace cycfi::q::midi_ci
{
   struct profile_id
   {
      std::uint8_t   byte1;      // 0x7E for a standard profile
      std::uint8_t   byte2;
      std::uint8_t   byte3;
      std::uint8_t   byte4;      // version, or the manufacturer's own
      std::uint8_t   byte5;      // level, or the manufacturer's own

      constexpr bool standard() const;
   };

   // The first four bytes, since a request carries 0x7F in the fifth.
   constexpr bool same_profile(profile_id const& a, profile_id const& b);

   struct profile
   {
      profile_id     id;

      bool           enabled;
      bool           permanent;     // its state cannot be changed
      std::uint16_t  channels;      // in use now
      std::uint16_t  max_channels;
   };

   namespace profile_status
   {
      enum
      {
         inquiry                    = 0x20,
         inquiry_reply              = 0x21,
         set_on                     = 0x22,
         set_off                    = 0x23,
         enabled_report             = 0x24,
         disabled_report            = 0x25,

The list is the caller’s and the responder writes through to it. Turning a profile on or off is the one request here that changes a device’s state, so the application reads it as a changed flag rather than as a message.

A permanent profile is one whose state cannot be changed, which the Common Rules give as an acoustic piano that always conforms to the piano profile. The rule there is that a reply states what actually holds rather than whether the request worked, so such a profile meets a request to turn it off by reporting that it is still on.

A profile that a request names carries 0x7F in its level byte, meaning as much of the profile as the device has. same_profile therefore matches profiles on their first four bytes. Comparing all five would never match what a device declared.

An inquiry addressed to the function block gets one reply per address that has profiles, channels first, then the group, and the function block last. That last reply marks the end of the sequence.

Initiator

A host that has found a device with initiator asks it which profiles it has, and turns them on and off.

namespace cycfi::q::midi_ci
{
   template <typename Next>
   class profile_initiator
   {
   public:
      explicit                profile_initiator(Next next);

                              template <typename Send>
      void                    ask(remote_device const& d, Send&& send);

                              template <typename Send>
      void                    turn_on(
                                 remote_device const& d
                               , std::uint8_t address, profile_id const& id
                               , Send&& send, std::uint16_t channels = 0);

                              template <typename Send>
      void                    turn_off(
                                 remote_device const& d
                               , std::uint8_t address, profile_id const& id
                               , Send&& send);

                              template <typename Send>
      void                    operator()(
                                 midi_1_0::sysex_view msg, Send&& send);
   };
}

ask sends a Profile Inquiry to the device’s function block. turn_on and turn_off send Set Profile On and Off to an address, and turn_on says how many channels the profile is to use. The profile initiator keeps no table, since what a device has is the application’s to keep. Next hears each profile named in a reply, or in a report a device sends to everyone, through profile_state(muid, address, id, enabled), and profiles_listed(muid) when the function block’s reply arrives, which ends the inquiry.

The application supplies the documents, and nothing else needs to:

struct my_device
{
   std::string_view property(std::string_view resource);

   int set_property(
      std::string_view resource, byte_span data);

   // Only if it keeps subscriptions.
   std::string_view subscribe(
      std::uint32_t muid, std::string_view resource);
   void unsubscribe(std::string_view id);
   void muid_invalidated(std::uint32_t target, bool all);
};

property returns a view into storage the device owns, which is the contract sysex_view has, and an empty view for a resource it does not have, which becomes a 404. set_property returns a status code and a device that has no such member refuses a Set with 405, the resource not being applicable. The responder handles the capabilities inquiry from what it was told, and handles a Get by calling property with the resource name and sending what it returns.

A document too long for one system exclusive is sent in chunks, which send_property does, and the header goes in the first chunk only. Where a receiver cannot keep up, flow control lets it take one chunk at a time: make_pe_ack reports that the last one arrived and make_pe_nak requests it again, and both carry the request id and the chunk number in the five detail bytes a MIDI-CI acknowledgement has.

Eight bit data cannot cross a seven bit wire, so mcoded7_encode and mcoded7_decode do what the Common Rules call Mcoded7: seven bytes become eight, the first carrying the top bit of each of the seven.

Subscriptions

A subscription keeps one resource in step between two devices so neither has to poll. The specification’s own example is a visual editor open in a host: turn a knob on the instrument and the editor follows, edit in the editor and the instrument follows.

The device holds the table, and Q moves the messages. A header-only library would have to choose how many subscribers it allows, and the device already knows.

subscribe is called when a subscription starts. It returns the id it gave that subscription, or an empty view to refuse, which becomes a 405. unsubscribe is called when either end sends the end command.

muid_invalidated is the least obvious of the three. A subscription also ends when an Invalidate MUID names either party, and that message belongs to the MIDI-CI responder rather than to this one, so Q passes it through and calls the hook. all is set when the target is this device, because it has then taken a new MUID and every subscription it held is over, whoever it was with.

When something changes, the device calls update and Q builds and chunks the message:

properties.update(
   subscriber, "sub1", ci::pe_command::full, my_state, send);

Choosing between partial, full and notify stays with the device, since the Common Rules make it a judgment about how much changed and whether it fits one chunk.

All three are optional, and detected the way set_property is. A device that keeps no subscriptions declares none of them and refuses a start with 405.
Replying to a ResourceList inquiry is the one thing the Common Rules make mandatory of a device that supports any of this. What is in that list is the device’s own business, so Q does not invent it.

Reading a value out of a header needs no JSON parser. The Common Rules hold a header to one line with no whitespace, keys in camel case of at most twenty characters, and values that are a number, a boolean or a string, which is narrow enough for header_value to scan. A library that may run in an audio callback has no business carrying a parser.

get, set, subscribe and unsubscribe each return the request id, or -1 when MaxRequests requests are already waiting. A Set goes out in chunks no longer than the device’s SysEx maximum, read from the remote_device. A reply in chunks is gathered, up to Capacity bytes, before Next hears it through property_reply(muid, request, status, header, data). One too long to gather is reported as 413, a request with no reply in the window as pe_reply::timed_out, and one the device refused with a NAK as pe_reply::refused.

An update for one of our subscriptions reaches property_update(muid, id, command, data) and is answered with 200. A subscription another device starts with us is the responder’s, so it is passed on. capabilities asks how many requests the device takes, and property_capabilities(muid, requests) has the answer.

Each initiator calls the hooks it has on Next when Next provides them, and passes on the other initiators' hooks. The initiators can be chained in any order in front of the responders, with one application stage after the last of them hearing every hook:

ci::profile_initiator profiles{my_app};          // my_app holds the responders
ci::property_initiator properties{profiles};
ci::initiator discovery{properties};             // every message enters here

What Is Not Covered

The notify message has its builder and is otherwise absent, the acknowledgement and the refusal having taken its place. Pagination has its header keys and no more, since paging a document is the device’s own affair. Has Property Data, sub-IDs 0x32 and 0x33, is reserved by the specification itself and has no layout to implement. The zlib encoding is absent, since it would put a compression library into a header-only audio library for one message type.

On the profile side, the added and removed reports and profile specific data can be built and read, but no responder sends them on its own, because only the device knows when it has gained or lost a profile.

The initiators send property data as ASCII only, Mcoded7 and zlib being for later, and send a Set’s chunks one after the other without waiting for the per-chunk acknowledgements of flow control. A profile inquiry a device refuses with a NAK ends without a profiles_listed.

Protocol Negotiation, category 1, is absent on purpose: version 1.2 deprecated it and the Stream Configuration Request replaced it.
