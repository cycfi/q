MIDI 2.0 Conformance

Overview

Q’s MIDI 2.0 implementation is tested in three ways: against the text of the specifications, clause by clause; as part of a device, under the MIDI Association’s MIDI 2.0 Workbench; and against MIDI implementations written by others. This page records what each covered and what is still to be tested.

The MIDI Association certifies products. A library has no port to plug into, so these tests run Q inside a device: example/midi2_endpoint in the repository, a MIDI 2.0 endpoint with a MIDI-CI responder, four profiles and three properties, one of which a host can set and subscribe to.

Device testing so far was on macOS 26.6 and Ubuntu 26.04, in October 2026.

Checklist

  • ✅ Universal MIDI Packet: every message type sized and skipped when not understood; nothing reserved sent

  • ✅ MIDI 2.0 channel voice messages, and translation to and from MIDI 1.0

  • ✅ Bit scaling between 7, 14 and 32 bit values

  • ✅ MIDI Polyphonic Expression

  • ✅ Endpoint discovery and stream configuration

  • ✅ Function block discovery

  • ✅ MIDI-CI discovery, MUIDs and collision handling

  • ✅ Invalidate MUID, including the subscriptions it ends

  • ✅ Profile inquiry, on a channel and on the function block

  • ✅ Profiles turned on and off, permanent profiles, and a NAK for a profile the device does not have

  • ✅ Property exchange: capabilities, Get and Set

  • ✅ Property data sent in chunks

  • ✅ Property subscriptions: start, update and end

  • ✅ Process inquiry capabilities

  • ✅ A MIDI-CI initiator written by others: JUCE

  • ✅ A host exchanging MIDI 2.0 voice messages: Logic Pro

  • ✅ macOS

  • ✅ Windows: all MIDI tests pass

  • ✅ Linux: all tests pass, the loopbacks over ALSA virtual ports included

  • ✅ A device run under the Workbench on Linux

  • ✅ Q as a MIDI-CI initiator: discovery, MUID collisions, and devices coming and going

  • ✅ Q asking a device it found for its profiles and properties: inquiry, Get, Set, subscriptions

  • ⬜ A device run under the Workbench on Windows

  • ⬜ A USB MIDI 2.0 device under the Workbench, with audio over USB Audio Class 2.0 beside it

The macOS MIDI-CI service runs no discovery on an endpoint created by an application, so it cannot be used as a test partner.

Against the Specification Text

Every rule Q implements has a test named for the clause that states it, and the test quotes the passage it checks. A test reads like "2.7 A profile that cannot be turned off says it is still on", so the test output can be read as a conformance report. The MIDI tests number 654 cases in 47 programs, and all pass on macOS, Windows and Linux.

With the MIDI 2.0 Workbench

The MIDI 2.0 Workbench (version 1.6.4p, built from source) is the MIDI Association’s test tool. It drives a device over a real connection and fills in the interoperability checklist. On macOS it reached the example endpoint two ways: over its MIDI 1.0 bridge, which carries MIDI-CI, and over UMP, which also carries the stream messages. On Linux it reached the endpoint over UMP through ALSA. On both, it needed a small change to list an endpoint that an application creates, since it looks only for hardware.

Automated Checks

Every automated check the Workbench runs on a MIDI-CI responder passes, with no errors, on macOS and on Linux:

CI1.2

The device takes a new MUID each time it is told to, and announces each one. The Workbench does this ten times and checks that the MUIDs differ.

CI2.5

The device accepts SysEx messages of at least 128 bytes.

CI4.2

When told its MUID is invalid, the device takes a new one and announces it with a Discovery message.

PE1.1

The device handles at least one property exchange request at a time.

PE2.4

The device accepts SysEx messages of at least 512 bytes.

Manual Checklist Items

The Workbench leaves these to the tester. Each was checked live against the endpoint, or by its clause test where the Workbench cannot send the message.

CI1.1, CI1.3

The device picks a new random MUID at start-up, within the range the specification allows.

CI2.1 to CI2.4

At start-up the device sends a Discovery message to all devices, carrying the identity and capabilities it declares.

CI3.1, CI3.2

The device replies to a Discovery message only when it is addressed to all devices or to this one, and sends the reply to the device that asked.

CI4.1

When another device’s MUID is invalidated, the device ends that device’s subscriptions.

CI5.1

The device invalidates its MUID when it shuts down.

PF2.1 to PF2.3

Asked for its profiles, the device lists which are on and which are off, for each channel, group and function block that has any, the function block last.

PF3.1 to PF3.6

Asked to turn a profile on or off, the device reports the profile’s new state. A profile that cannot change reports the state it is in. A request for a profile the device does not have gets a NAK.

PE2.1 to PE2.3

The device accepts a property Set sent in several chunks, also when the sender changes the chunk count partway, and drops the Set when a chunk is numbered zero.

Stream messages

The device answers Endpoint Discovery with its endpoint information, identity, name, product instance ID and stream configuration, and Function Block Discovery with its function block’s information and name.

UMP2.1

The device skips a packet of a reserved message type and reads the packet after it.

UMP2.2, UMP2.3

The device sends no reserved message types and leaves reserved fields at zero.

With Other Implementations

JUCE’s MIDI-CI Implementation

JUCE 9.0.3’s CapabilityInquiryDemo, a MIDI-CI initiator and responder written outside Cycfi, ran these exchanges with the example endpoint:

Discovery

JUCE found the device and read its identity, SysEx limit and profiles.

Endpoint Inquiry

The device returned its product instance ID.

Profile On and Off

The device turned a function block profile and a channel profile on and off, and reported each change to all devices.

Property Get

JUCE read ResourceList, DeviceInfo and X-Gain, a manufacturer resource.

Property Set

The device took a 4 byte Set, and a 1,202 byte Set that arrived in three chunks.

Subscribe

The device accepted a subscription to X-Gain, sent the subscriber the new value after a Set, and ended the subscription when asked.

Q asking

Q’s initiators found the JUCE device, kept it in their table across rounds, read its profile listing and got its ResourceList.

Logic Pro

Logic Pro 12.3.1 sends MIDI 2.0 channel voice messages to a Q endpoint and receives them from one, with velocity scaled as M2-115 specifies. It sends no MIDI-CI and no stream messages, so it tests the voice messages only.

What the Device Supplies

Some requirements are left to the device: the reply deadlines, the subscription table, the contents of ResourceList, the MIDI Message Report, and reports of a profile gained or lost. A device built on Q supplies them. The list, with the reason for each, is under What Q Does Not Do in MIDI.
