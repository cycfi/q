QPlug Setup and Installation

QPlug is part of Q. Its code lives in q_plug/, its examples in example/q_plug/ and its tests in test/q_plug/, and it is built from Q’s own CMake project with one option, Q_BUILD_PLUG, which is off by default.

Everywhere, QPlug needs C++20, CMake 3.21 or later, and network access the first time you configure. Configure fetches QPlug’s dependencies, each pinned; Dependencies, in Architecture, lists them and what each is for. The test validators are downloaded too, pinned and checksummed into a per-user cache, ~/.cache/cycfi/q_plug-validators, or under %LOCALAPPDATA% where there is no HOME. None of this is fetched while Q_BUILD_PLUG is off.

Building the VST3 means accepting Steinberg’s VST3 SDK license. See clap-wrapper’s README.

Getting the Code

git clone --recurse-submodules -b develop https://github.com/cycfi/q.git
cd q

The commands on this page run from there.

Building on macOS

macOS 11 or later, and the platform exercised most. Plugins are built as CLAP, VST3 and AudioUnit v2.

Prerequisites

Three things, and everything else is fetched at configure time.

Xcode Command Line Tools

xcode-select --install. Provides the C++20 compiler, the macOS SDK and frameworks, and git. Xcode 14 or later.

CMake and Ninja

brew install cmake ninja.

pkg-config

brew install pkg-config. Artist needs it at configure time, and configure stops with a message if it is missing.

The GUI draws through Artist’s Quartz2D backend, which is part of the system. There is no graphics toolchain to install: no Skia, no Cairo, and no fontconfig or freetype. The deployment target is macOS 11, the floor Artist’s own prebuilt bundles target, because Artist uses std::filesystem.

Build and Test

cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug

The directory name is CLion’s, so the IDE and the command line share one build. ctest runs Q’s own tests along with QPlug’s.

Every example lands in cmake-build-debug/products/ as a .clap, a .vst3 and a .component, each carrying the fonts and images it draws with, since Elements finds those only beside the plugin.

Always run cmake --build before ctest. A reconfigure on its own leaves the AUv2 bundle without its AudioComponents entry until the next build, a clap-wrapper quirk that QPlug works around at build time. The AU test refuses to install such a bundle, and reports why.

AudioUnits and auval

auval ships with macOS, so the AU tests need nothing installed. They do have a side effect worth knowing about: auval only finds components installed in the system, so the test copies the component into ~/Library/Audio/Plug-Ins/Components. After running it, AU hosts such as Logic Pro will list the plugin.

The test also compares the component version the system registry serves with the one the installed bundle declares, and restarts AudioComponentRegistrar once if they disagree. A stale registration is otherwise hard to recognize: the host reads the old description and offers the plugin with its old channel layout, which opens to an empty window.

Building on Windows

Windows builds and tests locally, and builds in CI. Plugins are built as CLAP and VST3; AudioUnit v2 is macOS only.

Prerequisites

Visual Studio

The Desktop development with C++ workload. Configure and build from a shell with the MSVC environment loaded, vcvars64.bat.

CMake and Ninja

choco install ninja, or the copies that ship with Visual Studio.

Git for Windows

Its bash is what runs the validation scripts. CMake finds it beside git.

The GUI draws with Artist’s Direct2D backend, which uses system libraries only, so there is no graphics toolchain to install.

Build and Test

cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug

Every example lands in cmake-build-debug/products/, each format in a folder of its own: CLAP/ for the .clap, VST3/ for the .vst3, and Standalone-<target>/ for the standalone app. Each carries the fonts and images it draws with, since Elements finds those only beside the plugin. The VST3 is built as a folder rather than a single file, because that is where a VST3 keeps its resources.

CI builds Windows but does not run the tests there, since the validation scripts are shell scripts. The tests run locally.

The MSVC runtime is chosen for the whole plugin build, static, because a plugin is not owed a redistributable by its host. Every dependency picks one otherwise, and mixing the two does not link.

Building on Linux

Linux builds in CI on Ubuntu with GCC. Plugins are built as CLAP and VST3, and the editor draws with Artist’s Cairo backend into the host’s X11 window.

Prerequisites

GCC or Clang

With C++20, and CMake 3.21 or later.

Packages

On Ubuntu or Debian, the ones CI installs:

sudo apt-get update
sudo apt-get install libcairo2-dev libfontconfig1-dev libfreetype6-dev \
   libharfbuzz-dev libwebp-dev libx11-dev libxcursor-dev libxrandr-dev \
   libasound2-dev pkg-config ninja-build

Cairo, fontconfig, FreeType, HarfBuzz and WebP are Artist’s; the X11 libraries are Elements' host; ALSA is the standalone app’s audio and MIDI.

Build and Test

cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug

Every example lands in cmake-build-debug/products/: the .clap, the .vst3, the standalone app, and a <name> Resources folder with the fonts and images that the app and the CLAP share.

The tests open each plugin’s editor, so they need a desktop. Without one, over SSH or in a container, see Without a Desktop. CI builds Linux with the tests off, since its runners have no display.

The Tests

ctest runs QPlug’s tests with Q’s: unit tests, tests that drive whole example plugins, and the format validators. The validators are downloaded on first configure, so nothing has to be installed. Testing QPlug covers all of it, including running without a desktop.

Build Options

Q_BUILD_PLUG

Build QPlug, its examples and its tests. OFF.

Q_BUILD_EXAMPLES

Build the examples, Q’s and QPlug’s. ON.

Q_BUILD_TEST

Build and register the tests, Q’s and QPlug’s. ON. Turning it off also skips fetching the validators.

Q_PLUG_DOWNLOAD_VALIDATORS

Download the pinned clap-validator and pluginval. ON.

CLAP_VALIDATOR, PLUGINVAL

Paths to your own validator binaries. Either one given takes precedence over the download.

Q_PLUG_VALIDATOR_DIR

Where the downloaded validators are cached, instead of the per-user default.

The Examples

The examples live under example/q_plug/, and each is built in every format its platform has.

gain

The smallest, and the place to start: a mono gain with one automatable parameter, a volume in decibels, and a fader with a console taper for it.

delay

Two parameters, a delay time and a feedback amount, shown on dials with labeled marks.

anna_1 to anna_5

Anna, one polyphonic synthesizer in five stages, each a complete plugin. Stage 1 is the oscillator and its envelope, stage 2 adds the resonant filter, stage 3 a chorus, stage 4 draws the envelopes as a control the user shapes directly, and stage 5 adds factory presets.

dexter

Dexter, a six operator FM synth that plays DX7 patches and cartridges, with Q’s FM engine inside and an editor for every parameter.

A plugin declares one channel layout, and another layout is another plugin. Both effects are mono, so a host offers them on mono tracks; on a stereo track, a host such as Logic runs a mono plugin as dual mono, one instance per channel. The synths have no audio input and two outputs, and their feature list includes instrument, which is what keeps a host from offering one as an insert.

The Standalone App

Every example also builds a standalone app: the plugin’s CLAP, hosted by clap-wrapper in an application of its own, with its own audio and MIDI devices. It is the quickest way to try a plugin, since it needs no host. Audio goes through RtAudio, from Q’s QIO, and MIDI through RtMidi.

A plugin asks for one in its build, beside the formats:

STANDALONE_CONFIGURATIONS
   standalone "QPlug Gain" "com.qplug.gain"

The three values are the configuration’s name, which ends the app’s target name (q_plug-gain_standalone), then the app’s name and its id, which repeats the plugin’s id.

The app lands with the other products:

Platform The app

macOS

products/QPlug Gain.app

Windows

products/Standalone-q_plug-gain_standalone/QPlug Gain.exe

Linux

products/QPlug Gain

It opens the plugin’s editor in a window of its own. At first it plays through the system’s default output, takes the default input, and listens to every MIDI input that is connected. On macOS, the first launch of an effect asks for microphone access; allow it, or the app waits.

Settings

The audio devices are chosen in an Audio/MIDI Settings window:

  • macOS: the application menu, Audio/MIDI Settings. It chooses the output, the input and the sample rate; MIDI always listens to every input.

  • Windows: the window menu, from the icon at the left of the title bar or Alt+Space. Audio/MIDI Settings chooses the audio API (WASAPI or ASIO), the output, the input, the sample rate, the buffer size and the MIDI inputs. The same menu mutes the input, and saves, loads or resets the plugin’s state.

  • Linux: no settings window. The app uses the default devices and every MIDI input.

On macOS and Windows, the app remembers the devices and the plugin’s state from one run to the next, in a folder named after the plugin’s id:

  • macOS: ~/Library/Application Support/clap-wrapper-standalone/<id>/

  • Windows: %LOCALAPPDATA%\clap-wrapper-standalone\<id>\

settings.clapwrapper there is what the app last closed with, and defaults.clapwrapper what it first started with. Delete the folder to start over. A state saved from the app (File, Save As… on macOS, Save State on Windows) is the same file format, and opens again with File, Open… or Load State.

Building Outside the Project

Every example is also a project of its own, so a plugin can be written and built outside Q. Copy an example’s folder anywhere, and configure it with Q_ROOT set to your Q checkout, as an absolute path or one relative to the folder. With Q set to that checkout:

cp -R "$Q/example/q_plug/gain" /tmp/gain
cd /tmp/gain
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_ROOT="$Q"
cmake --build build

The Quick Start of Your First Plugin: Gain has the Windows commands too, and how to start the result.

The prerequisites are the same as above. Configured this way, the example’s CMakeLists.txt adds Q from Q_ROOT with Q_BUILD_PLUG on and Q’s own examples and tests off, and calls q_plug_settings, which gives the plugin’s directory the settings a plugin needs. The products land in build/products/. The validation tests are part of Q’s own build and are not registered.
