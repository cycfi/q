= Presenter

include::../common.adoc[]

== Overview

A presenter is a plugin's editor. It builds the GUI (element tree; see
below) when the host opens a window, binds each control to a parameter,
and owns the view that tree lives in. A plugin that returns `nullptr` from
`make_presenter` is headless: the host gets no editor, and everything else
about the plugin works as before.

An element is https://github.com/cycfi/elements[Elements]' unit of
interface: anything that sizes itself, draws and takes a click, from a
`box` to a slider. They compose by holding each other, and that is what
makes a tree: a margin holds a fader, a tile holds a row of them, and the
view holds the roots, one per layer, the background last.

An element carries no coordinates. The tree is walked instead: the limits
come up from the leaves, layout and draw go back down, working out each
element's bounds on the way, and a click is hit-tested down the same path.
Elements are therefore light enough to be built afresh for every editor,
and the content's limits bound the window.

== Presenter Example

A presenter subclass implements `on_attach`. The base `presenter` makes the
view, handles the zoom keys every plugin shares, keeps the editor inside the
content's limits, keeps the scale, and builds the {header}: a presenter
calls `make_header` and places the result at the top. This is the `gain`
example's presenter, in full. It places no header:

[source,c++]
----
#include <q_plug/presenter.hpp>
...
namespace q_plug = cycfi::q_plug;
namespace elements = cycfi::elements;

struct gain_controller : q_plug::controller
{
   enum { volume_id };
   parameter const&     volume_param() const;
   ...
};
...
class gain_presenter : public q_plug::presenter
{
public:
                        gain_presenter(gain_controller& ctl);

protected:

   void                 on_attach(elements::view& view_) override;

private:

   gain_controller&     _ctl;
};
----

`on_attach` is called with the freshly made view. It builds the content and
binds it:

[source,c++]
----
#include <elements.hpp>
...
using namespace cycfi::elements;

auto constexpr bkd_color = rgba(35, 35, 37, 255);
...
void gain_presenter::on_attach(elements::view& view_)
{
   // A fader: the decibel taper of a console, marked and labeled at the
   // usual points over the parameter's range.
   auto const& param = _ctl.volume_param();
   db_scale scale{param.min(), param.max()};

   auto track = slider_labels_db<10>(
      slider_marks_db<40>(basic_track<5, true>(), scale),
      0.8,                                   // Label font size (relative)
      scale
   );

   auto fader = share(
      slider(align_center(image{"slider-white.png", 1.0/4}), track)
   );

   bind(gain_controller::volume_id, fader, scale);

   view_.content(
      align_center(vmargin({20, 20}, hold(fader))),
      box(bkd_color)
   );
}
----

The editor has one control, bound to one parameter.

image::q_plug/gain-editor.svg[alt="the gain editor and what its one bind connects", width=520px, role=center]

The presenter holds a reference to its own controller, given to it when the
plugin makes the three parts. It holds no reference to the {processor}. Everything it
reads and everything it changes goes through the {controller}.

== Binding a Control

image::q_plug/presenter-bind.svg[alt="what one bind wires up", width=620px, role=center]

`bind` is the one call that ties a control to a parameter, and it makes
three connections at once: the control shows the parameter, what the user
does to the control reaches the host as an edit, and a drag on it is
bracketed as one gesture.

The control takes the parameter's current value as it is bound, and follows
the {controller}'s model for as long as the view lives.

Any number of controls may share a parameter. Each is bound in its own
right, and all of them follow the model, so a dial and a text box showing
the same value stay together.

NOTE: A binding uses the control's own callback, its `on_change`, or a
button's `on_click`. A plugin that acts when a parameter moves overrides
`edit_parameter` on the controller.

== When the User Moves the Control

The control reports its travel, the binding maps it back to a value, and
`edit_parameter` sends the value to the controller and on to the host.

A drag is bracketed. `begin_edit` goes out as the drag starts and
`end_edit` as it ends, so the host records the drag as one movement. All
three go out on the main thread, in the order the user made them:

image::q_plug/bind-gesture.svg[alt="one drag, from the fader to the host", width=700px, role=center]

== When the Host Moves the Parameter

The other direction needs no plugin code. The host's value
arrives on the audio thread and is stored there; the models are brought up
to date on the main thread, and every control bound to one follows and is
redrawn.

image::q_plug/host-automation.svg[alt="a value from the host reaching the control", width=700px, role=center]

Only the models whose value has changed are assigned, so a value the host
echoes back in the middle of a drag leaves the control the user is holding
where it is. The {controller} page describes where a parameter is kept and
what `update_models` does.

== The Mapping

The mapping carries the control's travel, 0 to 1, to the
parameter's value and back: `position(value)` one way and `value(position)`
the other.

`scale` belongs to `gain`, and it is an
https://github.com/cycfi/elements[Elements] `db_scale` over the
parameter's own range:

[source,c++]
----
#include <q_plug/presenter.hpp>
#include <elements.hpp>
...
namespace q_plug = cycfi::q_plug;
using namespace cycfi::elements;

struct gain_controller : q_plug::controller
{
   parameter const&     volume_param() const;
   ...
};
...
class gain_presenter : public q_plug::presenter
{
   ...
   void on_attach(cycfi::elements::view& view_) override
   {
      auto const& param = _ctl.volume_param();
      db_scale scale{param.min(), param.max()};
      ...
   }

   gain_controller&     _ctl;
};
----

That is the taper of a console fader. The parameter is linear in
decibels; the fader spreads the range around unity over more of its travel
and compresses the quiet end, where a decibel matters less.

Any type with the same two functions is a mapping. A {parameter} is one,
over its own range and taper, and is what a control is usually bound with.
`gain` binds with a `db_scale` because its fader needs a taper the
parameter does not have.

== Controls With Several Values

`bind` takes a control with one value: one setter and one callback. An
element that carries several values exposes each as a control of its own,
with its own setter and callback:
https://github.com/cycfi/elements[Elements]' `bindable_proxy` does that
for any element, and `curve_editor` exposes each axis of each of its points
that way, through `x_of` and `y_of`.

`gain` has no such control, so the rest of this section works from
`anna_4`, the fourth stage of the virtual analog synth: a voice through
a filter and a chorus, with an envelope for the amplifier and another for
the filter. Its envelopes are the subject here. Each is a curve editor:
one shape whose corners are dragged.

image::q_plug/adsr-proxies.svg[alt="the drawn envelope and the four values it carries", width=620px, role=center]

Three corners carry the four values: the peak's distance from the start
is the attack, the tail's end's from the plateau is the release, and the
corner between them is both the decay, by its distance, and the sustain
level, by its height. The editor exposes each axis of a point as a proxy,
and the presenter binds it with a mapping:

[source,c++]
----
#include <q_plug/presenter.hpp>
#include <elements.hpp>
...
namespace q_plug = cycfi::q_plug;
using namespace cycfi::elements;

namespace adsr                                  // anna_4's envelope editor
{
   constexpr std::size_t peak = 1, corner = 2, plateau = 3, finish = 4;

   struct stage                                 // a time as a share of its stage
   {
      double position(double v) const;
      double value(double pos) const;
      q_plug::parameter const* param;
   };

   std::shared_ptr<basic_curve_editor> make();
}

class anna_presenter : public q_plug::presenter
{
   ...
   void on_attach(cycfi::elements::view& view_) override
   {
      auto const& params = ctrl().parameters();
      auto env = adsr::make();
      int attack;                               // the attack parameter's index
      ...
      bind(attack, x_of(env, adsr::peak), adsr::stage{&params[attack]});
      ...
   }
};
----

`x_of(env, i)` is a `curve_value`: its `value(v)` sets that axis of that
point, its `on_change` is the callback the binding sets, and its
`on_gesture` the one the editor calls as a drag along that axis begins
and ends. The mapping carries the parameter's travel to the point's
unit: `stage` makes a time a share of its stage's width. With those, an
envelope's four values are bound, each similar to how a slider is bound,
and `link` binds a value with the parameter as its own mapping:

[source,c++]
----
auto link = [&](int id, auto control)
{
   bind(id, control, params[id]);
};

auto link_envelope =
   [&](auto env, int attack, int decay, int sustain, int release)
   {
      bind(attack, x_of(env, adsr::peak), adsr::stage{&params[attack]});
      bind(decay, x_of(env, adsr::corner), adsr::stage{&params[decay]});
      link(sustain, y_of(env, adsr::corner));
      link(sustain, y_of(env, adsr::plateau));
      bind(release, x_of(env, adsr::finish), adsr::stage{&params[release]});
   };
----

A proxy is outside the element tree, so the presenter keeps every proxy it
binds for as long as the view lives. A proxy holds its editor by a weak
reference, as the binder holds every control. A point's position is in the
editor's unit square; the mapping and each parameter's taper convert it to
the parameter's units, milliseconds for the three times and a percentage
for the sustain level.
A point that follows another, as the plateau follows the corner, is
bound to the same parameter, and a host moving it moves both.

A drag then moves every value the corner carries, each as an edit of its
own:

image::q_plug/adsr-gesture.svg[alt="one corner dragged, two parameters edited", width=660px, role=center]

A gesture on an axis begins the first time the drag changes it and ends
with the release, so the host records a movement for each of the two
parameters, and the editor reports a value only when it has changed. From
the controller on, the path is the one described above. A slider's drag is
reported through the view, where the presenter hooks it in one place; a
proxy is outside the tree, so the presenter hooks the proxy's own gesture
callback.

The host's automation arrives the same way it does for a slider, and ends
at the proxy:

image::q_plug/adsr-automation.svg[alt="a value from the host reaching one value of the control", width=740px, role=center]

The proxy sets the value of its axis, so only that one value of the
editor is written. A proxy is outside the tree and has nothing of its own
to redraw: `refresh_target` returns the element it forwards to, and the
binding refreshes that element. A host moving two of the editor's
parameters notifies two models, and each writes its own value into the
same shape.

== The View

The view is dynamically created only as needed. It exists only while the
host has an editor open and every step of its life is on the main thread.
When the user wants to open a view (e.g. in a DAW), the presenter creates
it and builds its content, then attaches it into the host's window. When
the user closes the plugin window, the presenter takes it down again.

NOTE: Where the platform allows a view before there is a window to put it
in, as Cocoa does, the view is made as soon as the editor is created, so
the content is built and measured before the window arrives. Where it does
not, as on Windows and X11, the view is made once the parent exists.

The view, in its entirety, is destructed once the editor window is closed:
the bindings come off their models, the gestures and the proxies are
dropped, and the elements are destroyed. The parameters and their models
belong to the controller and are untouched, so an editor closed and opened
again comes back on the same values.

== Size and Scale

The editor opens at the size the plugin declares, `info().view_size`,
taken at the scale the last session was left at. The content's own limits
bound it from then on, and the host is given those limits before it sizes
anything: a fixed layout allows only its own size. When the limits
change, the presenter calls `request_resize` for a window to match. The
host may set a size in return, or leave the window as it is.

The editor's
https://cycfi.github.io/elements/elements/v1.0/layout/scale.html[scale] is
owned by the controller, so a reopened editor and a restored session both
come back at the scale they were left at. Zooming is the same in every
plugin: the action key, Command on macOS and Control elsewhere, with plus,
minus and zero, the same three in the main menu, and the buttons at the
right of the header. The stops are a tenth apart, from half size to
double. The {zoom} page covers the stops, where the scale is kept, and
how a size in logical units becomes the host's own.

== The Header

`make_header` builds the row along the top of the editor: a main menu at
the left, the preset the plugin is on beside it, and at the right the zoom
buttons and a logo, if there is one. Everything on it works through the
controller, so there is nothing to wire. A plugin calls it from
`on_attach` and puts it at the top of its content: `anna_5` holds it
first in the `vtile` that carries its panels.

image::q_plug/header-parts.svg[alt="the header and the virtual that builds each part", width=620px, role=center]

The header is built by calling these virtual functions:

* `make_main_menu`
* `make_preset_menu`
* `header_items`
* `make_zoom_buttons`
* `logo`

A plugin customizes the header by overriding one of them. The {header}
page describes each part, the standard menu items, and what an override
is given.

== Declaration

```c++
struct view_sink
{
   virtual                 ~view_sink() = default;
   virtual bool            request_resize(elements::extent size) = 0;
};

class presenter
{
public:

   using element_ptr = elements::element_ptr;

                           presenter(controller& ctl);
   virtual                 ~presenter();

                           template <typename Control, typename Mapping>
   void                    bind(int index, std::shared_ptr<Control> control
                            , Mapping mapping);

   bool                    create(elements::extent size);
   bool                    attach(void* parent, elements::extent size);
   void                    detach();
   void                    show(bool show);

   elements::extent        size() const;
   elements::view_limits   limits() const;
   bool                    resize(elements::extent size);

   bool                    request_resize(elements::extent size);

   void                    zoom(float scale);
   float                   zoom() const;
   void                    zoom_in();
   void                    zoom_out();
   void                    actual_size();

   static constexpr float  zoom_min = 0.75f;
   static constexpr float  zoom_max = 1.5f;

   void                    sink(view_sink& s);
   elements::view*         view() const;
   controller&             ctrl() const;

   float                   pixel_scale() const;

protected:

   virtual void            on_attach(elements::view& view_);
   virtual void            on_detach();

   virtual element_ptr     make_header();
   virtual element_ptr     make_main_menu();
   virtual element_ptr     make_preset_menu();
   virtual element_ptr     make_zoom_buttons();
   virtual element_ptr     logo();

   using row = std::vector<element_ptr>;
   virtual void            header_items(row& items);

   using menu = std::vector<element_ptr>;
   virtual void            preset_menu_items(menu& items);
   virtual void            view_menu_items(menu& items);
   virtual void            plugin_menu_items(menu& items);
   virtual void            about_menu_items(menu& items);
};

using presenter_ptr = std::unique_ptr<presenter>;
```

== Client Interface

The `presenter` is a base class, meant to be derived from and not
instantiated directly. The client writes a class derived from it,
constructed with the plugin's {controller}, and overrides `on_attach` to
build the editor's content and bind its controls. Both functions below do
nothing unless overridden.

`void on_attach(elements::view& view_) override;` ::
    Build the content and bind it. Called on the main thread with the
    freshly made view, once per view, before the view is sized. `view_`
    is the view `p.view()` returns for as long as that editor is open.
`void on_detach() override;` ::
    Called on the main thread as the view is taken down, before its
    bindings, gestures and elements go.

NOTE: `on_attach` is called again for every editor the host opens. Build
the content there and keep nothing between one view and the next: the
elements, the bindings and the gestures all go with the view.

The header functions, `make_header`, `make_main_menu`, `make_preset_menu`,
`make_zoom_buttons`, `logo`, `header_items` and the four `_menu_items`
functions, are overridden to customize the header. See {header}, with a
worked example of a plugin adding to the row and to the menu.

== Expressions

The scale functions, `zoom`, `zoom_in`, `zoom_out`, `actual_size`,
`zoom_min` and `zoom_max`, the user's scale, and `pixel_scale`, the
display's, are covered in {zoom}.

=== Notation

`p`                  :: Object of a type derived from `presenter`.
`ctl`                :: Object of a type derived from `controller`.
`index`              :: An `int`, a parameter's index in
                        `ctl.parameters()`.
`control`            :: A `std::shared_ptr` to an
                        https://github.com/cycfi/elements[Elements] control,
                        or to a `bindable_proxy`.
`mapping`            :: An object with `position(value)` and
                        `value(position)`.
`parent`             :: The host's window, as a `void*`.
`size`               :: Object of type `elements::extent`.
`show`               :: A `bool`.
`s`                  :: Object of a type derived from `view_sink`.

=== Constructor

[cols="1,1"]
|===
| Expression               | Semantics

| `presenter(ctl)`         | Construct a `presenter` given `ctl`
                             (the plugin's controller).
|===

`presenter` is non-copyable.

`plugin` makes the controller first and passes it to `make_presenter`, then
installs itself as the sink. A plugin's presenter keeps a reference of its
own controller type, so it can read its parameters through that
controller's own accessors.

=== Accessors

[cols="1,1,1"]
|===
| Expression               | Semantics                          | Return Type

| `p.ctrl()`               | Get the controller the presenter
                             was made with.                     | `controller&`
| `p.view()`               | Get the live view, null when there
                             is none.                           | `elements::view*`
| `p.size()`               | Get the view's size, zero without
                             a view.                            | `elements::extent`
| `p.limits()`             | Get the content's limits,
                             `full_limits` without a view.      | `elements::view_limits`
|===

=== Mutators

[cols="1,1,1"]
|===
| Expression               | Semantics                          | Return Type

| `p.sink(s)`              | Set the sink the presenter's
                             requests to the host go to.        | `void`
|===

=== Operation

[cols="1,1,1"]
|===
| Expression                        | Semantics                     | Return Type

| `p.bind(index, control, mapping)` | Bind `control` to the parameter
                                      at `index`, through
                                      `mapping`.                    | `void`
| `p.request_resize(size)`          | Request a size from the host.
                                      False if the host declines it
                                      or there is no sink.          | `bool`
| `p.resize(size)`                  | Size the view, within the
                                      limits. False if the size
                                      requested is not the size it
                                      got, or there is no view.     | `bool`
| `p.create(size)`                  | Make the view and build its
                                      content, where it may exist
                                      before there is a window.     | `bool`
| `p.attach(parent, size)`          | Put the view into the host's
                                      window, making it first if it
                                      does not exist yet.           | `bool`
| `p.detach()`                      | Take the view down.           | `void`
| `p.show(show)`                    | Refresh the view when the host
                                      shows the editor (`show` is
                                      true).                        | `void`
|===

`bind` needs the view, so it is called from `on_attach` and nowhere else.
The control shows the parameter from that moment, and what the user does to
it reaches the host as an edit, bracketed as one gesture. `mapping` carries
the control's travel, 0 to 1, to the parameter's value and back.

The limits determine the minimum and maximum size of the view. The limits
are read before a window is sized. A size beyond the limits is clamped to
the nearest allowed size, and `resize` returns false to report it. A fixed
layout allows one size only, so every other size is refused that way.

`resize` is the host setting the view's size. `request_resize` runs in the
opposite direction: the plugin requests a size, which the host may or may
not permit. The presenter issues this request itself when the content's
limits change, so that the window keeps up with an editor whose layout has
grown or shrunk. A plugin seldom needs to call it.

[NOTE]
====
A window the user can expand or shrink is one whose content is resizable:
an element whose minimum
https://cycfi.github.io/elements/elements/v1.0/layout/limits.html[limits]
are below its maximum in x or y. Every element starts with `full_limits`,
unconstrained in both directions, and has a fixed size where its minimum
and maximum are equal.

An editor left unconstrained reports a maximum of
https://cycfi.github.io/elements/elements/v1.0/layout/limits.html[`full_extent`],
so the window is freely resizable. A plugin whose editor has a fixed size
wraps its content in
https://cycfi.github.io/elements/elements/v1.0/layout/sizing.html[`fixed_size`],
so `can_resize` returns false and the host offers no resizing.
====

A plugin never calls `create`, `attach`, `detach` or `show`. The host's
editor requests arrive through `base_plugin`, the class that adapts the
plugin to CLAP, and `plugin`, which derives from it, passes each one to
the presenter. The `size` it passes is always `info().view_size`, the size
the plugin declared, at a scale of one. The view is constructed at the
saved scale, so the editor opens at that declared size scaled.

`create` makes the view early where the platform allows it. Otherwise, it
does nothing and still returns `true`; `attach` makes the view once the
window exists. `detach` runs from the destructor as well as from the host,
so a presenter destroyed while its editor is open takes the view down with
it.

=== Example

Make a presenter whose editor is one dial, bound to the parameter at index
0 of the plugin's controller:

```c++
#include <q_plug/presenter.hpp>
#include <elements.hpp>
...
namespace q_plug = cycfi::q_plug;
namespace elements = cycfi::elements;
using namespace cycfi::elements;

class dial_presenter : public q_plug::presenter
{
public:

   dial_presenter(q_plug::controller& ctl)
    : q_plug::presenter{ctl}                                    <1>
   {}

protected:

   void on_attach(elements::view& view_) override               <2>
   {
      auto const& param = ctrl().parameters()[0];
      auto knob = share(dial(radial_marks<20>(basic_knob<60>())));

      bind(0, knob, param);                                     <3>

      view_.content(                                            <4>
         margin({20, 20, 20, 20}, hold(knob)),
         box(rgba(35, 35, 37, 255))
      );
   }
};
```

<1> Construct the base `presenter` with the plugin's controller.
<2> Build the editor in `on_attach`, called with each new view.
<3> Bind the dial to parameter 0, with the parameter as its own mapping.
<4> Place the dial over a background in the view.

See <<_client_interface>> for more info.
