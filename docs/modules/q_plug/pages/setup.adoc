= QPlug Setup and Installation

QPlug is part of Q. Its code lives in `q_plug/`, its examples in
`example/q_plug/` and its tests in `test/q_plug/`, and it is built from Q's
own CMake project with one option, `Q_BUILD_PLUG`, which is off by default.

Everywhere, QPlug needs {cpp}20, CMake 3.21 or later, and network access
the first time you configure. Configure fetches Elements (which brings
Artist), CLAP, clap-wrapper and nlohmann json, each pinned; clap-wrapper
downloads the VST3 SDK, Apple's AudioUnitSDK and RtMidi, which the
standalone apps use with Q's own RtAudio; and the test validators
are downloaded, pinned and checksummed into a per-user cache,
`~/.cache/cycfi/q_plug-validators`, or under `%LOCALAPPDATA%` where there
is no `HOME`. None of this is fetched while `Q_BUILD_PLUG` is off.

[IMPORTANT]
====
Building the VST3 means accepting Steinberg's VST3 SDK license. See
clap-wrapper's README.
====

== Building on macOS

macOS 11 or later, and the platform exercised most. Plugins are built as
CLAP, VST3 and AudioUnit v2.

=== Prerequisites

Three things, and everything else is fetched at configure time.

Xcode Command Line Tools:: `xcode-select --install`. Provides the {cpp}20
compiler, the macOS SDK and frameworks, and git. Xcode 14 or later.

CMake and Ninja:: `brew install cmake ninja`.

pkg-config:: `brew install pkg-config`. Artist asks for it at configure
time, and configure stops with a message if it is missing.

The GUI draws through Artist's Quartz2D backend, which is part of the
system. There is no graphics toolchain to install: no Skia, no Cairo, and
no fontconfig or freetype. The deployment target is macOS 11, the floor
Artist's own prebuilt bundles target, because Artist uses
`std::filesystem`.

=== Build and test

[,sh]
----
git clone --recurse-submodules -b develop https://github.com/cycfi/q.git
cd q
cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug
----

The directory name is CLion's, so the IDE and the command line share one
build. `ctest` runs Q's own tests along with QPlug's.

Every example lands in `cmake-build-debug/products/` as a `.clap`, a
`.vst3` and a `.component`, each carrying the fonts and images it draws
with, since Elements finds those only beside the plugin.

[IMPORTANT]
====
Always run `cmake --build` before `ctest`. A reconfigure on its own leaves
the AUv2 bundle without its `AudioComponents` entry until the next build, a
clap-wrapper quirk that QPlug works around at build time. The AU test
refuses to install such a bundle, and says so.
====

=== AudioUnits and auval

auval ships with macOS, so the AU tests need nothing installed. They do
have a side effect worth knowing about: auval only sees components
installed in the system, so the test copies the component into
`~/Library/Audio/Plug-Ins/Components`. After running it, AU hosts such as
Logic Pro will list the plugin.

The test also compares the component version the system registry serves
with the one the installed bundle declares, and restarts
`AudioComponentRegistrar` once if they disagree. A stale registration is
otherwise hard to recognize: the host reads the old description and offers
the plugin with its old channel layout, which opens to an empty window.

== Building on Windows

Windows builds and tests locally, and builds in CI. Plugins are built as
CLAP and VST3; AudioUnit v2 is macOS only.

=== Prerequisites

Visual Studio:: The Desktop development with {cpp} workload. Configure and
build from a shell with the MSVC environment loaded, `vcvars64.bat`.

CMake and Ninja:: `choco install ninja`, or the copies that ship with
Visual Studio.

Git for Windows:: Its bash is what runs the validation scripts. CMake
finds it beside git.

The GUI draws with Artist's Direct2D backend, which uses system libraries
only, so there is no graphics toolchain to install.

=== Build and test

[,sh]
----
cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug
----

Every example lands in `cmake-build-debug/products/`, each format in a
folder of its own: `CLAP/` for the `.clap`, `VST3/` for the `.vst3`, and
`Standalone-<target>/` for the standalone app. Each carries the fonts and
images it draws with, since Elements finds those only beside the plugin.
The VST3 is built as a folder rather than a single file, because that is
where a VST3 keeps its resources.

CI builds Windows but does not run the tests there, since the validation
scripts are shell scripts. The tests run locally.

The MSVC runtime is chosen for the whole plugin build, static, because a
plugin is not owed a redistributable by its host. Every dependency picks
one otherwise, and mixing the two does not link.

== The tests

`ctest` runs two kinds of test on every platform.
xref:testing.adoc[Testing QPlug] covers both in full.

The unit tests cover the parts of QPlug that are plain code, checked
without a host: MIDI event translation, block splitting at event frames,
parameter tapers, the GUI scale arithmetic, and Elements' `bindable_proxy`.
Alongside them are tests that drive a whole example plugin through its CLAP
entry point, so the audio a synth produces and the presets it loads are
checked end to end.

The validation tests run the standard validator for each format against the
built plugin, one ctest test per format per example. They are the scripts in
`q_plug/scripts/`, which can be run by hand as well as through ctest;
`q_plug/scripts/README.md` lists the environment variables that pick which
plugin to validate.

`Q_PLUG_SKIP_GUI_TESTS`:: pluginval opens the editor, which needs a desktop
to put a window on. Set this in the environment ctest runs in, over SSH or
in a service, and the editor tests are left out. The run says so, so a
skipped editor never passes quietly.

== The validators

clap-validator and pluginval are downloaded once, pinned by version and
verified against a recorded sha256. Nothing has to be installed for
`ctest` to work.

To use your own installs instead, pass `-DCLAP_VALIDATOR=...` and
`-DPLUGINVAL=...`, which always win, or set
`-DQ_PLUG_DOWNLOAD_VALIDATORS=OFF` to have CMake look for installed copies.
A validator that cannot be found makes its test skip rather than fail: the
scripts exit 77, which ctest reports as SKIPPED.

== Build options

Q_BUILD_PLUG:: Build QPlug, its examples and its tests. `OFF`.

Q_BUILD_EXAMPLES:: Build the examples, Q's and QPlug's. `ON`.

Q_BUILD_TEST:: Build and register the tests, Q's and QPlug's. `ON`.
Turning it off also skips fetching the validators.

Q_PLUG_DOWNLOAD_VALIDATORS:: Download the pinned clap-validator and
pluginval. `ON`.

CLAP_VALIDATOR, PLUGINVAL:: Paths to your own validator binaries. Either
one given takes precedence over the download.

Q_PLUG_VALIDATOR_DIR:: Where the downloaded validators are cached, instead
of the per-user default.

== The examples

The examples live under `example/q_plug/`, and each is built in every format
its platform has.

gain:: The smallest, and the place to start: a mono gain with one
automatable parameter, a volume in decibels, and a fader with a console
taper for it.

delay:: Two parameters, a delay time and a feedback amount, shown on dials
with labeled marks.

anna_1 to anna_5:: One polyphonic synthesizer in five stages, each
a complete plugin. Stage 1 is the oscillator and its envelope, stage 2 adds
the resonant filter, stage 3 a chorus, stage 4 draws the envelopes as a
control the user shapes directly, and stage 5 adds factory presets.

A plugin declares one channel layout, and a plugin that wants another is
another plugin. Both effects are mono, so a host offers them on mono
tracks; on a stereo track, a host such as Logic runs a mono plugin as dual
mono, one instance per channel. The synths have no audio input and two
outputs, and their feature list says `instrument`, which is what keeps a
host from offering one as an insert.

== Building Outside the Project

Every example is also a project of its own, so a plugin can be written and
built outside Q. Copy an example's folder anywhere, and configure it with
`Q_ROOT` set to your Q checkout, as an absolute path or one relative to the
folder. With `Q` set to that checkout:

[,sh]
----
cp -R "$Q/example/q_plug/gain" /tmp/gain
cd /tmp/gain
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_ROOT="$Q"
cmake --build build
----

The Quick Start of xref:tutorials/gain.adoc#_quick_start[Your First Plugin: Gain]
has the Windows commands too, and how to start the result.

The prerequisites are the same as above. Configured this way, the
example's `CMakeLists.txt` adds Q from `Q_ROOT` with `Q_BUILD_PLUG` on and
Q's own examples and tests off, and calls `q_plug_settings`, which gives
the plugin's directory the settings a plugin needs. The products land in
`build/products/`. The validation tests are part of Q's own build and are
not registered.

xref:tutorials/gain.adoc[Your First Plugin: Gain] covers the file line by
line, and what to rename to make the copy a plugin of your own.
