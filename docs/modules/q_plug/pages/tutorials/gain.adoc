= Your First Plugin: Gain

include::../common.adoc[]

== Overview

`example/q_plug/gain` is the smallest QPlug plugin: a mono gain with one
automatable parameter, a volume in decibels, and a console fader to move
it.

image::qplug/gain-standalone.png[alt="QPlug Gain running as a standalone app", title="QPlug Gain, running as a standalone app on macOS", width=400px, align=center]

Small as it is, it has one of everything a plugin is made of: a
{controller} that declares the parameter, a {processor} that applies it, a
{presenter} that draws the fader, and the file that makes all three and
gives the host the plugin's identity. {architecture} describes how those
parts fit together; this page reads the code, in the order the plugin
makes them.

== The Controller

The {controller} comes first, because the other two are handed it.

[source,c++]
----
class gain_controller : public q_plug::controller
{
public:

   using decibel = cycfi::q::decibel;

   enum { volume_id };

   // The fader runs from silence, the 24 bit floor, up to +10 dB.
   static constexpr decibel silence = cycfi::q::dB(-144.0);
   static constexpr decibel max_volume = cycfi::q::dB(10.0);

   parameter_list       parameters() const override;

   decibel              volume() const;
   parameter const&     volume_param() const;
};
----

`volume_id` is the parameter's index in the list `parameters()` returns,
which is how every part of the plugin addresses it. The two constants are
the fader's range. The accessors serve the other two parts: `volume`
gives the processor the value as a `q::decibel`, and `volume_param` gives
the presenter the declaration, which is where the range can be read.

[source,c++]
----
inline gain_controller::decibel gain_controller::volume() const
{
   return get_parameter<decibel>(volume_id);
}

inline gain_controller::parameter const&
gain_controller::volume_param() const
{
   return parameters()[volume_id];
}
----

`parameters` is the one function a controller must write:

[source,c++]
----
parameter_list gain_controller::parameters() const
{
   static parameter params[] =
   {
      parameter{ 1, "Volume", 0_dB }.range(silence.rep, max_volume.rep)
   };

   return { params };
}
----

Each entry is a {parameter}. The first argument, `1`, is the parameter's
id. The host saves and automates the parameter by it, so it is the
parameter's identity for the life of the plugin: never reuse an id and
never change one. The id and the index are separate on purpose. QPlug
translates between them, and the plugin's own code only ever uses the
index.

An initial value of `0_dB` makes this a decibel parameter, with `dB` as
its unit, and is what lets `volume` read it back with
`get_parameter<decibel>`. A Debug build asserts that the type asked for
matches. A decibel parameter starts with a range of -60 to +12 dB; `range`
replaces it with the fader's own, in plain numbers, hence `.rep`.

The array is `static` because `parameter_list` is a range over it, not a
copy, so it has to outlive the call.

That is the whole controller. The base holds the value where both threads
can reach it, as {architecture} describes, and saves it with the state.

== The Processor

[source,c++]
----
class gain_processor : public q_plug::processor
{
public:

                        gain_processor(gain_controller& ctl);

   channel_config       channels() const override { return {1, 1}; }

   void                 activate() override;
   void                 reset() override;

   void                 process(
                           in_channels const& in
                         , out_channels const& out) override;

private:

   float                gain() const;

   gain_controller&     _ctl;
   q::one_pole_lowpass  _gain_lp{0.0f};
};
----

The {processor} base, `q_plug::processor`, is a Q `audio_stream_base`,
so `process` takes Q's `in_channels` and `out_channels`, the same
`multi_buffer` a Q program works with. `channels` declares one input and
one output; without it a processor is stereo in and out. A plugin has one
channel layout, so this is a mono plugin, and a host offers it on mono
tracks.

The processor keeps the controller, which is where the volume is read, and
a Q xref:ROOT:reference/misc/one_pole_lowpass.adoc[`one_pole_lowpass`] to
smooth the gain with.

[source,c++]
----
namespace
{
   // A parameter change slews at this rate instead of stepping, which
   // would click.
   constexpr auto smoothing = 4_Hz;
}

gain_processor::gain_processor(gain_controller& ctl)
 : _ctl(ctl)
{}

// The stream is known here, and stays put until the next activation.
void gain_processor::activate()
{
   _gain_lp.cutoff(smoothing, sps());
}

// A transport jump: take up the current gain rather than sliding to it.
void gain_processor::reset()
{
   _gain_lp = gain();
}
----

The host gives the plugin its sample rate when it activates it, and `sps()`
holds that rate by the time `activate` is called. The smoother's cutoff
depends on the rate, so it is set there, once, rather than on every block.

`reset` is called right after `activate`, and again by the host whenever
the processor should drop what it carried over, as on a transport jump.
Assigning to a `one_pole_lowpass` sets its output, so the smoother starts
at the current gain instead of gliding up to it from wherever it was.

[source,c++]
----
void gain_processor::process(in_channels const& in, out_channels const& out)
{
   auto target = gain();
   auto frames = in.frames.size();

   for (std::size_t f = 0; f != frames; ++f)
   {
      auto g = _gain_lp(target);
      for (std::size_t ch = 0; ch != in.size(); ++ch)
         out[ch].begin()[f] = in[ch].begin()[f] * g;
   }
}

// The bottom of the fader is silence.
float gain_processor::gain() const
{
   auto db = _ctl.volume();
   return db <= gain_controller::silence ? 0.0f : q::lin_float(db);
}
----

`process` reads the target once, then passes every frame through the
smoother, so a change moves the gain at 4 Hz instead of jumping to it.
Reading once per call is enough. QPlug cuts the host's block where the
host's events fall and calls `process` once per piece, each with the
parameter values in force for it, so a volume change still lands on the
frame the host put it on.

`gain` turns decibels into a factor with `q::lin_float`, from Q's
xref:ROOT:reference/units/decibel.adoc[decibel]. At the bottom of the
fader it returns 0, true silence, rather than the very small factor
-144 dB converts to.

Nothing here locks, allocates or talks to the host. The processor reads a
parameter and writes samples.

== The Presenter

[source,c++]
----
class gain_presenter : public q_plug::presenter
{
public:
                        gain_presenter(gain_controller& ctl);

protected:

   void                 on_attach(elements::view& view_) override;

private:

   gain_controller&     _ctl;
};
----

The {presenter} passes the controller on to its base, which owns the
view, and keeps it as `gain_controller` too, to reach `volume_param`.

[source,c++]
----
void gain_presenter::on_attach(elements::view& view_)
{
   // A fader: the decibel taper of a console, marked and labelled at the
   // usual points over the parameter's range.
   auto const& param = _ctl.volume_param();
   db_scale scale{param.min(), param.max()};

   auto track = slider_labels_db<10>(
      slider_marks_db<40>(basic_track<5, true>(), scale),
      0.8,                                   // Label font size (relative)
      scale
   );

   auto fader = share(
      slider(align_center(image{"slider-white.png", 1.0/4}), track)
   );

   bind(gain_controller::volume_id, fader, scale);

   view_.content(
      align_center(vmargin({20, 20}, hold(fader))),
      box(bkd_color)
   );
}
----

The view exists only while the host has the editor open, so the content is
built in `on_attach`, which is called with each new view.

`db_scale` is Elements' console taper. It maps decibels to the fader's
travel and back, gives the range around unity most of the travel, and
squeezes the quiet end into the bottom. It is made from the parameter's own
range, read from the declaration, so the fader's range and the
parameter's cannot differ. The same scale places the ticks
(`slider_marks_db`) and writes the labels beside them
(`slider_labels_db`), with the infinity sign at the bottom, since the
range reaches silence.

The thumb is an image from the plugin's resources, `slider-white.png`,
drawn at a quarter of its pixel size. Elements loads images from beside
the plugin, which is why the build copies it there.

`share` makes the fader a `std::shared_ptr`, which is what `bind` takes,
and `hold` puts that same fader into the content. `bind` then connects it
to the parameter both ways, through the scale. What the user does to the
fader reaches the host as an edit, bracketed as one gesture. What the host
does to the parameter, from automation or a restored session, moves the
fader. The bindings go when the view does.

`view_.content` stacks its elements with the first on top: the fader, over
a dark background.

NOTE: Gain leaves out the standard {header} along the top of the editor.
To show it, a presenter calls `make_header` from `on_attach` and puts it at
the top of the content.

== The Plugin

`gain.cpp` makes the three parts and declares the plugin's identity:

[source,c++]
----
namespace cycfi::q_plug
{
   controller_ptr make_controller()
   {
      return std::make_unique<gain_controller>();
   }

   processor_ptr make_processor(controller& ctl)
   {
      return std::make_unique<gain_processor>(
         static_cast<gain_controller&>(ctl));
   }

   presenter_ptr make_presenter(controller& ctl)
   {
      return std::make_unique<gain_presenter>(
         static_cast<gain_controller&>(ctl));
   }

   plugin_info const& info()
   {
      static char const* const features[] =
      {
         "audio-effect",
         "mono",
         nullptr
      };

      static plugin_info const i =
      {
         "com.qplug.gain",              // id
         "QPlug Gain",                  // name
         "QPlug",                       // vendor
         "",                            // url
         "",                            // manual_url
         "",                            // support_url
         "0.1.1",                       // version
         "Simple mono gain plugin",     // description
         features,
         {400, 350},                     // view size
         1                              // state version
      };
      return i;
   }
}
----

These four functions, in `cycfi::q_plug`, are all QPlug requires a plugin
to supply. The controller is made first, and the processor and the presenter
are each handed it as a plain `controller&`; the cast gets gain's own type
back. This is the only place the three parts meet.

`plugin_info` is the plugin's identity to the host. The id is in
reverse domain form, and matches the build's `BUNDLE_IDENTIFIER`. The
feature list is null terminated, and `audio-effect` and `mono` are CLAP's
standard features for a mono effect. The view size is the size the editor
opens with. The state version stays at 1 until what a saved parameter value
means changes.

== The Build

`example/q_plug/gain/CMakeLists.txt` builds the plugin in every format:

[source,cmake]
----
# The plugin's own code, plus the q_plug adapter it links.
add_library(q_plug_gain_impl STATIC
   gain.cpp
   gain_processor.cpp
   gain_controller.cpp
   gain_presenter.cpp
)
# q_plug is PRIVATE on purpose: the clap-wrapper format modules must link it
# and Elements but must not inherit their compile options, since Elements
# exports -fobjc-arc and clap-wrapper's Cocoa code is manual retain/release.
# clap is PUBLIC because the entry shim compiled into each module needs it.
target_link_libraries(q_plug_gain_impl PRIVATE q_plug PUBLIC clap)
q_plug_add_host(q_plug_gain_impl QPlugGain)

# Assemble CLAP, VST3 and AUv2 from the one implementation.
make_clapfirst_plugins(
   TARGET_NAME q_plug-gain
   IMPL_TARGET q_plug_gain_impl

   OUTPUT_NAME "QPlug Gain"

   ENTRY_SOURCE "${Q_PLUG_ROOT}/src/clap/q_plug_entry.cpp"

   BUNDLE_IDENTIFIER "com.qplug.gain"
   BUNDLE_VERSION   "${q_plug_VERSION}"

   COPY_AFTER_BUILD FALSE
   WINDOWS_FOLDER_VST3 TRUE      # a bundle, so its fonts go inside

   PLUGIN_FORMATS ${Q_PLUG_PLUGIN_FORMATS}

   # A standalone app around the same CLAP, to try it without a host.
   STANDALONE_CONFIGURATIONS
      standalone "QPlug Gain" "com.qplug.gain"

   ASSET_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/products"

   AUV2_MANUFACTURER_NAME "QPlug"
   AUV2_MANUFACTURER_CODE "QPlg"
   AUV2_SUBTYPE_CODE      "QGan"
   AUV2_INSTRUMENT_TYPE   "aufx"
)

q_plug_separate_import_libs(q_plug-gain)
q_plug_fix_auv2_plist(q_plug-gain)
q_plug_add_resources(q_plug-gain
   "${CMAKE_CURRENT_SOURCE_DIR}/resources/slider-white.png")
q_plug_add_validation_tests(gain "QPlug Gain" aufx QGan QPlg)
----

The plugin's code and the QPlug adapter are one static library,
`q_plug_gain_impl`. `q_plug_add_host` compiles Elements' host layer into it
with its view class named after `QPlugGain`. On macOS every Objective-C
class name is shared by the whole process, so two plugins in one host would
otherwise define the same class. The prefix must be a valid identifier,
and unique to the plugin.

`make_clapfirst_plugins` is clap-wrapper's. It builds a module per format
from that one library, with QPlug's entry shim compiled into each.
`Q_PLUG_PLUGIN_FORMATS` is CLAP and VST3, and AUv2 as well on macOS. The
modules are named for `OUTPUT_NAME` and land in `products/` under the build
directory. `STANDALONE_CONFIGURATIONS` adds one more product, a standalone
app named `QPlug Gain` that hosts the same CLAP with its own audio and
MIDI devices, through RtAudio and RtMidi. The AUv2 codes are the
component's identity to macOS, and `aufx` registers it as an effect.

The four QPlug functions after it finish the job:

`q_plug_separate_import_libs`:: Gives each format its own directory for
the import library and export file MSVC writes with every link. The
formats share one output name, so without it two links running at once
write the same `.lib` and one of them fails. It does nothing with other
toolchains.

`q_plug_fix_auv2_plist`:: Keeps the AudioComponents entry in the AUv2
bundle across a reconfigure, working around a clap-wrapper quirk. It does
nothing off macOS.

`q_plug_add_resources`:: Copies the fonts Elements draws with, and the
files named, here the fader's thumb, into every format's bundle. Off
macOS, a CLAP is a plain library with no bundle and the standalone app a
plain executable, so their resources go in a folder beside them,
`QPlug Gain Resources`. `WINDOWS_FOLDER_VST3` builds the Windows VST3 as a
folder, which gives its resources somewhere to go.

`q_plug_add_validation_tests`:: Registers one ctest test per format, each
running that format's validator on the product: `gain.clap`, `gain.vst3`
and, on macOS, `gain.au`, which is why it is given the AU type, subtype and
manufacturer codes.

== Running

Build everything, as {setup} describes, then run gain's tests:

[,sh]
----
cmake -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DQ_BUILD_PLUG=ON
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug -R gain
----

The build leaves the products in `cmake-build-debug/products/`:

* macOS: `QPlug Gain.app`, `QPlug Gain.clap`, `QPlug Gain.vst3` and
  `QPlug Gain.component`.
* Windows: `CLAP/QPlug Gain.clap`, `VST3/QPlug Gain.vst3` and
  `Standalone-q_plug-gain_standalone/QPlug Gain.exe`, each with its
  resources.
* Linux: `QPlug Gain`, the standalone app, `QPlug Gain.clap` and
  `QPlug Gain.vst3`, with the `QPlug Gain Resources` folder the app and the
  CLAP share.

The standalone app is the quickest way to try the plugin, since it needs
no host: start it, and the editor opens in a window of its own.

The build does not install the plugins. To load one in a host, copy it
to the host's plugin folder:

* macOS: `~/Library/Audio/Plug-Ins/CLAP`, `~/Library/Audio/Plug-Ins/VST3`
  or `~/Library/Audio/Plug-Ins/Components`. The AU test has already put the
  component there.
* Windows: a CLAP goes in `%LOCALAPPDATA%\Programs\Common\CLAP` or
  `%COMMONPROGRAMFILES%\CLAP`, together with the `QPlug Gain Resources`
  folder beside it. A VST3 goes in your host's VST3 folder.
* Linux: a CLAP goes in `~/.clap` or `/usr/lib/clap`, together with the
  `QPlug Gain Resources` folder beside it. A VST3 goes in `~/.vst3`.

Insert QPlug Gain on a mono track and open its editor. Drag the fader, and
automate Volume from the host; the fader follows.

== Components Used

[cols="1,2", options="header"]
|===
| Component              | Role

| {controller}           | Holds Volume; `get_parameter<decibel>` reads it
| {parameter}            | Declares Volume: id, name, initial value, range
| {processor}            | The channel layout, `activate`, `reset` and `process`
| {presenter}            | `on_attach` builds the fader; `bind` links it to Volume
| `q_plug::plugin_info`  | The plugin's identity to the host
| xref:ROOT:reference/misc/one_pole_lowpass.adoc[one_pole_lowpass] | Smooths the gain
| xref:ROOT:reference/units/decibel.adoc[decibel] | `lin_float`: decibels to a linear factor
| `elements::db_scale`   | The fader's console taper, ticks and labels
|===
