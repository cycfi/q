= MIDI

include::../common.adoc[]

== Overview

Q reads MIDI as typed messages. A message on the wire, three bytes of MIDI 1.0 or a packet of MIDI 2.0, becomes a small value type with accessors, a `note_on` with its `key()` and `velocity()`, and is handed to a processor: a class with one function call operator for each message it handles. Everything in the MIDI part of the library is built around that one shape, and none of it depends on a device or an operating system. *q_io* supplies the device end; a plugin host or a file may supply it instead.

image::midi-layers.svg[alt="The layers of Q MIDI", width=750px, align=center, title="Bytes or packets come in on the left and typed messages reach a processor on the right. A chain is written for one protocol, and takes the other through a translator.", link={imagesdir}/midi-layers.svg]

[cols="1,3"]
|===
| In the figure     | What it is

| bytes             | MIDI 1.0 bytes, from a device or a file.
| `byte_reader`     | Bytes to whole messages: running status kept, system exclusive gathered.
| packets           | Universal MIDI Packets, from a device or a host.
| `packet_reader`   | Packets to whole messages: system exclusive and text gathered.
| `dispatch`        | A raw message, or a packet, to the typed message it holds.
| stages            | `parameter_reader`, `cc14_reader`, `mode_reader` and `mpe_reader` for MIDI 1.0; `per_note_reader`, `stream_responder` and `endpoint_inquiry` for MIDI 2.0. See {midi_stages}.
| `to_midi2`        | MIDI 1.0 messages widened to MIDI 2.0.
| `to_midi1`        | MIDI 2.0 messages narrowed to MIDI 1.0.
| processor         | Your class, with an overload for each message it handles.
|===

Both protocols are covered, each in its own namespace. MIDI 1.0 is the protocol of five-pin cables and of most instruments in use: a status byte and up to two data bytes of 7 bits each. MIDI 2.0 is its superset: the same messages at 16 and 32 bits, new ones that address a single note of a chord, all carried in Universal MIDI Packets of one to four 32 bit words. A packet stream can carry MIDI 1.0 messages too, so the two meet in one place.

xref:reference/midi/conformance.adoc[MIDI 2.0 Conformance] records how the implementation was tested: against the specifications, under the MIDI 2.0 Workbench, and against other implementations.

== Endpoints and Devices

A processor can be either a device or an endpoint, or both.

An **endpoint** is where a UMP connection terminates. It has a name, a serial number, a manufacturer and model, the protocols it takes, and a topology: a list of function blocks, each a named set of groups with a direction. Anything at the end of a packet connection is one, whichever way the notes flow.

A **device** is something with a MUID that implements MIDI Capability Inquiry: discovery, profiles, property exchange. On a packet connection a MUID belongs to a function block, not to the endpoint, so an endpoint with three MIDI-CI capable blocks holds three devices.

Neither implies the other, and all four combinations exist:

* **A USB pad controller that only sends notes.** An endpoint, not a device. A host learns its name and its one function block from the stream messages, and nothing in system exclusive replies: Function Block Info declares a MIDI-CI version of `0x00` for none.
* **A virtual synth that makes sound and nothing else.** An endpoint, not a device. The common case.
* **A keyboard workstation with profiles and a patch list.** Both. Its keyboard, its pads and its control surface are three function blocks, each with its own MUID, so a host configures one without touching the others.
* **A guitar controller with a string per group.** Both: one connection with one name, six function blocks, six MUIDs, so a profile goes on for one string alone.
* **An instrument on a five-pin cable that implements MIDI-CI.** A device, not an endpoint. That shipped in 2020, before there was any UMP hardware, and it runs over ordinary system exclusive, so there is a MUID and no groups, no function blocks and no endpoint.
* **A plugin that serves its patch list through the host's system exclusive routing.** A device, not an endpoint.
* **A plugin that only makes sound.** Neither.

**A plugin is neither a device nor an endpoint by default.** It receives MIDI through the host's port, and the port is the endpoint. A plugin becomes a device by implementing MIDI-CI, and an endpoint by opening a port of its own.

A plugin receives MIDI through the host's port; the port is the endpoint, and a plugin that implements MIDI-CI is a device.

Q follows the same split. `endpoint_description` and `stream_responder` are the endpoint, one per connection, and they are built on the packet reader. `midi_ci::responder` is the device, one per MUID, and it is built on `sysex_view`, which either reader produces. The same MIDI-CI code serves a device on a five-pin cable and a function block inside an endpoint, without knowing which.

=== Declaring a Role

A class takes a role by declaring its member function: `endpoint()` for the endpoint, `device()` for the device.

```c++
#include <q/midi/ump_processor.hpp>
#include <q/midi/endpoint.hpp>
#include <q/midi/ci.hpp>
...
namespace midi2 = cycfi::q::midi_2_0;
namespace ci = cycfi::q::midi_ci;

struct my_instrument : midi2::processor
{
   using midi2::processor::operator();
   void operator()(midi2::note_on msg, std::size_t time);

   midi2::endpoint_description&  endpoint();        // the endpoint role
   ci::device_description const& device() const;    // the device role
};
```

```c++
std::uint32_t rng();                // the client's random number generator
...
my_instrument instrument;
auto send = [](midi2::packet const& p) { /* to the host */ };

midi2::stream_responder stream{instrument, send, instrument};
ci::responder           discovery{instrument, rng};
```

A responder takes the description it needs from the class, so one class can be the synth, the endpoint and the device at once. A class that is only a synth has neither member and is passed as the processor alone. A caller without such a class passes a description to the responder directly.

`endpoint()` returns a non-const reference because a granted Stream Configuration Request changes the protocol in use, and the endpoint reports the current state. The class keeps that field, and the change shows there.

The property hooks in {midi_ci}, `property()` and `set_property()` among them, are members of a device class as well, so the class that provides `device()` can also serve property inquiries.

== Namespaces

```c++
namespace cycfi::q::midi     { /**...**/ }   // what both protocols share
namespace cycfi::q::midi_1_0 { /**...**/ }   // MIDI 1.0
namespace cycfi::q::midi_2_0 { /**...**/ }   // MIDI 2.0 and the packet
namespace cycfi::q::midi_ci  { /**...**/ }   // MIDI Capability Inquiry
```

`midi` holds what both protocols share: `message_base`, which every message derives from; the default no-op `processor`; the controller names in `cc`; the note helpers; the per-note messages `note_pitch`, `note_pressure` and `note_timbre`; and the `Processor` concept, in `concepts::midi`. The system messages and `sysex_view` are named there as well, since MIDI 2.0 carries them unchanged. Each protocol's namespace names what it uses of these, so `midi_1_0::cc` and `midi_2_0::cc` are both `midi::cc`.

== The Layers

The wire::
A reader makes whole messages from incoming data. See {midi_readers}. `byte_reader` takes MIDI 1.0 bytes, keeps running status, and gathers a system exclusive message until it ends. `packet_reader` takes packets and gathers what spans several of them: system exclusive in its 7 bit and 8 bit forms, and the stream messages that carry text. A message too long for a reader's buffer is dropped whole, never truncated.

Dispatch::
`dispatch` turns one raw message or one packet into the type it holds and calls the processor with it. See {midi_messages}, {midi2_messages} and {midi_processor}. The MIDI 2.0 `dispatch` hands the MIDI 1.0 voice messages and the system messages a packet may carry to the MIDI 1.0 `dispatch`, so a MIDI 2.0 processor receives those as the MIDI 1.0 types they are.

The stages::
A stage reads meaning out of messages. See {midi_stages}. It is a processor proxy: it handles the messages it reads and forwards the rest inward. `parameter_reader` assembles the six controllers that spell a registered or unregistered parameter. `cc14_reader` joins the coarse and fine halves of a 14 bit controller. `mode_reader` turns controllers 120 and up into the channel mode messages they are. `mpe_reader` reads a zone's channels as messages about single notes, and `per_note_reader` reads MIDI 2.0's per-note messages as the same three: `note_pitch`, `note_pressure` and `note_timbre`.

Between the protocols::
`to_midi1` and `to_midi2` are stages too. See {midi_translation}. One narrows MIDI 2.0 messages to MIDI 1.0 and drops what MIDI 1.0 cannot say; the other widens MIDI 1.0 messages to MIDI 2.0. A processor written for either protocol can therefore be fed by either kind of stream. The resolution scaling they use keeps zero, the maximum and the center of a bipolar value exact.

The endpoint::
Before sending notes, a host requests the device's description: its name and serial number, its manufacturer, family and model, the protocol it takes, and the function blocks it is made of. See {midi_endpoint}. The stream messages carry these requests and their replies. `stream_responder` replies from a description the device supplies, and `endpoint_inquiry` sends the requests and gathers the replies. MIDI Capability Inquiry carries a second exchange over universal system exclusive. See {midi_ci}.

== Chaining

Dispatch is called once, at the front, and stages nest in one expression:

```c++
#include <q/midi/parameters.hpp>
#include <q/midi/controllers.hpp>
...
namespace midi = cycfi::q::midi_1_0;

struct my_synth : midi::processor { ... };
my_synth synth;                          // the client's synth
midi::raw_message msg;                   // from a reader
std::size_t time;
...
auto chain = midi::parameter_reader{midi::cc14_reader{synth}};
midi::dispatch(msg, time, chain);
```

Here `synth` is a processor, `cc14_reader` wraps it, and `parameter_reader` wraps that. A message goes to the outermost stage first.

NOTE: Order matters where two stages read the same controllers. See {midi_stages}.

== What Q Does Not Do

Every message type either MIDI protocol defines has a processor overload. Q leaves the following to the application.

=== No Clock

`q_lib` has no timeouts and sends nothing on a timer. MIDI-CI allows a responder three seconds to reply, and a sender of jitter reduction timestamps sends a clock every 250 milliseconds; Q reads the messages involved and runs neither timer.

A library that may run in an audio callback has no clock of its own, and the caller already has one. `endpoint_inquiry` keeps the time passed to `poll` when it sends a request, `started_at()` returns it, and the caller decides when a request has gone unanswered too long. For the same reason `cc14_reader` delivers the coarse half of a 14 bit controller as soon as it arrives. See {midi_endpoint} and {midi_stages}.

=== Device State

Q handles the protocol for these, and the device class supplies the data:

* **`ResourceList`** is the one property document the Common Rules make mandatory. It lists the properties of one particular device, so Q gets it from the device class's `property()` hook.
* **A property subscription** requests an update whenever a property changes. Q replies to the start and the end of a subscription. The device class keeps the table of subscribers through its `subscribe` and `unsubscribe` hooks, and when a property changes the application calls `update` with a full, partial or notify command; Q builds and chunks the message.
* **A profile** is turned on and off by Q, in the list the device declares. Profile Added and Profile Removed reports, and profile specific data, can be built and read. No responder sends them, since a device gains or loses a profile only through the application.
* **A MIDI Message Report** requests every controller value and every note the device is holding, and the reply is a stream of MIDI produced from that state. A device that declares the capability handles the message itself; one that does not gets a NAK.

=== Sending

* **`set_chord_name` has no field constructor.** Its fields number fourteen: two chords with six alterations between them. A received one is read like any other message. See {midi2_messages}.
* **The MIDI-CI initiators send ASCII only.** Property data goes out in ASCII, never Mcoded7 or `zlib`, and a Set's chunks go one after the other without per-chunk flow control. See {midi_ci}.

=== Deliberate Absences

* **Protocol Negotiation**, MIDI-CI category 1, is omitted. Version 1.2 deprecated it, and the Stream Configuration Request in {midi_endpoint} replaced it.
* **The `zlib` property encoding** is absent. It would put a compression library into a header-only audio library for the sake of one message type. `Mcoded7` is implemented; it is bit packing.
* **Property pagination** has its header keys named. Paging a document is left to the device class.
* **Has Property Data**, sub-IDs 0x32 and 0x33, is reserved by the specification itself and has no defined layout to implement.
* **The property notify message** has a builder only. The acknowledgement and the refusal took its place.

=== Mixed Data Sets

A mixed data set can carry a firmware image, so `packet_reader` passes each mixed data set packet on as it arrives, without a buffer large enough to assemble one. A system exclusive message is bounded and small, and is assembled. See {midi_readers}.
