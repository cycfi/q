= MIDI

include::../common.adoc[]

== Overview

Q reads MIDI as typed messages. A message on the wire, three bytes of MIDI 1.0 or a packet of MIDI 2.0, becomes a small value type with accessors, a `note_on` with its `key()` and `velocity()`, and is handed to a processor: a class with one function call operator for each message it cares about. Everything in the MIDI part of the library is built around that one shape, and none of it depends on a device or an operating system. *q_io* supplies the device end; a plugin host or a file may supply it instead.

image::midi-layers.svg[alt="The layers of Q MIDI", width=750px, align=center, title="Bytes or packets come in on the left and typed messages reach a processor on the right. A chain is written for one protocol, and takes the other through a translator.", link={imagesdir}/midi-layers.svg]

Both protocols are covered, each in its own namespace. MIDI 1.0 is the protocol of five-pin cables and of most instruments in use: a status byte and up to two data bytes of 7 bits each. MIDI 2.0 is its superset: the same messages at 16 and 32 bits, new ones that address a single note of a chord, all carried in Universal MIDI Packets of one to four 32 bit words. A packet stream can carry MIDI 1.0 messages too, so the two meet in one place.

== Namespaces

```c++
namespace cycfi::q::midi_1_0 { /**...**/ }   // MIDI 1.0
namespace cycfi::q::midi_2_0 { /**...**/ }   // MIDI 2.0 and the packet
namespace cycfi::q::midi_ci  { /**...**/ }   // MIDI Capability Inquiry
```

The same name means the same thing in each: `midi_1_0::note_on` and `midi_2_0::note_on`, `midi_1_0::processor` and `midi_2_0::processor`, `midi_1_0::dispatch` and `midi_2_0::dispatch`. Code written for one protocol reads like code written for the other.

== The Layers

The wire::
A reader takes what arrives and gives whole messages. `byte_reader` takes MIDI 1.0 bytes, keeps running status, and gathers a system exclusive message until it ends. `packet_reader` takes packets and gathers what spans several of them: system exclusive in its 7 bit and 8 bit forms, and the stream messages that carry text. A message too long for a reader's buffer is dropped whole, never truncated.

Dispatch::
`dispatch` turns one raw message or one packet into the type it holds and calls the processor with it. See {midi_messages} and {midi_processor}. The MIDI 2.0 `dispatch` hands the MIDI 1.0 voice messages and the system messages a packet may carry to the MIDI 1.0 `dispatch`, so a MIDI 2.0 processor sees those as the MIDI 1.0 types they are.

The stages::
A stage reads meaning out of messages. It is a processor that wraps a processor: it handles the messages it knows and forwards the rest inward. `rpn_reader` assembles the six controllers that spell a registered or unregistered parameter. `cc14_reader` joins the coarse and fine halves of a 14 bit controller. `mode_reader` turns controllers 120 and up into the channel mode messages they are. `mpe_reader` reads a zone's channels as messages about single notes, and `per_note_reader` reads MIDI 2.0's per-note messages as the same three: `note_pitch`, `note_pressure` and `note_timbre`.

Between the protocols::
`to_midi1` and `to_midi2` are stages too. One narrows MIDI 2.0 messages to MIDI 1.0 and drops what MIDI 1.0 cannot say; the other widens MIDI 1.0 messages to MIDI 2.0. A processor written for either protocol can therefore be fed by either kind of stream. The resolution scaling they use keeps zero, the maximum and the centre of a wheel exact.

The endpoint::
A MIDI 2.0 device says what it is when asked. The stream messages carry that conversation, `stream_responder` answers it from a description the device supplies, and the `midi_ci` namespace holds the discovery part of MIDI-CI, which runs over universal system exclusive.

== Chaining

Dispatch is called once, at the front, and stages nest in one expression:

```c++
namespace midi = cycfi::q::midi_1_0;

auto chain = midi::rpn_reader{midi::cc14_reader{my_synth}};
midi::dispatch(msg, time, chain);
```

Here `my_synth` is a processor, `cc14_reader` wraps it, and `rpn_reader` wraps that. A message goes to the outermost stage first.

NOTE: The order matters where two stages read the same controllers. Data entry, controllers 6 and 38, is the value of a parameter to `rpn_reader` and a coarse and fine pair to `cc14_reader`. With `rpn_reader` outermost, as above, a parameter's data entry is taken as the parameter's; the other way round, `cc14_reader` would take every data entry first.
