= MIDI 1.0 Messages

include::../../common.adoc[]

== Overview

MIDI is one way to control DSP parameters in a more meaningful, and musical way. Here, we talk about MIDI as a standardized messaging protocol. MIDI messages include note-on and note-off messages, control change messages, program change messages, and pitch bend messages, as well as tempo, time signature, and other performance data.

This page covers the MIDI 1.0 messages: each one a small value type that holds the bytes of the message and reads its fields through accessors. They are what a {midi_processor} receives. See {midi2_messages} for their MIDI 2.0 counterparts, and {midi} for how the messages, the processors and the rest of Q's MIDI fit together.

== Use Case

A pianist plays a chord, presses the sustain pedal, lifts both hands, and the chord keeps sounding until the pedal comes up. On the wire that is three note ons, a `control_change` on controller 64 with a value of 127, three note offs the synth must not act on yet, and a final `control_change` with a value of 0. The synth below holds every note released while the pedal is down and releases them all when it lifts.

```c++
struct sustaining_synth : midi::processor
{
   using midi::processor::operator();

   void operator()(midi::note_on msg, std::size_t)
   {
      voice(msg.key()).on(msg.velocity());
   }

   void operator()(midi::note_off msg, std::size_t)
   {
      if (_pedal)
         _held.set(msg.key());               // release when the pedal lifts
      else
         voice(msg.key()).off();
   }

   void operator()(midi::control_change msg, std::size_t)
   {
      if (msg.controller() != midi::cc::sustain)
         return;
      _pedal = msg.value() >= 64;             // down from 64 upward
      if (!_pedal)
      {
         for (std::size_t key = 0; key != 128; ++key)
            if (_held.test(key))
               voice(key).off();
         _held.reset();
      }
   }

   bool              _pedal = false;
   std::bitset<128>  _held;
};
```

== Namespaces

```c++
namespace cycfi::q::midi     { /**...**/ }   // what both protocols share
namespace cycfi::q::midi_1_0 { /**...**/ }   // MIDI 1.0
```

The MIDI 1.0 messages live in `namespace midi_1_0`. The MIDI 2.0 messages have a namespace of their own, `midi_2_0`, where a message of the same name means the same thing at a higher resolution. What both protocols share lives in `namespace midi`: `message_base`, the controller names in `cc`, and the note helpers. See {midi_cc} and {midi_notes}. Both protocol namespaces name those too, so `midi_1_0::cc::sustain` and `midi::cc::sustain` are the same thing.

== Generic MIDI Messages

The MIDI 1.0 message is basically an array of `std::uint8_t` with sizes 1 to 3, encapsulated in a `struct`. A whole MIDI 1.0 message as bytes, system exclusive included, travels as `q::byte_span`, an alias of `std::span<std::uint8_t const>` from {base}, Q wide and not MIDI's own; it is what the readers of {midi_readers} take and a MIDI 1.0 {midi_sink} sends.

```c++
using byte_span = std::span<std::uint8_t const>;   // namespace cycfi::q
```

The message structs:

```c++
struct message_base {}; // Base class for all messages

template <int size_>
struct message : message_base
{
   static constexpr int const size = size_;
   std::uint8_t data[size];
};

struct message1 : message\<1>
{
   message1() = default;
   constexpr message1(raw_message msg);
};

struct message2 : message\<2>
{
   message2() = default;
   constexpr message2(raw_message msg);
};

struct message3 : message\<3>
{
   message3() = default;
   constexpr message3(raw_message msg);
};
```

== Raw MIDI Messages

Generic MIDI messages are constructed from `raw_message`, which is essentially a `std::uint32_t` encapsulated in a `struct` that holds the 24-bits MIDI 1.0 message, encoded as little-endian:

image::raw-midi-message.svg[alt="The four bytes of a raw MIDI message", width=720px, align=center, title="A raw MIDI message", link={imagesdir}/raw-midi-message.svg]

[cols="1,3"]
|===
| In the figure | What it is

| data          | The `std::uint32_t` the message is held in.
| unused        | Bits 31 to 24. A MIDI 1.0 message is three bytes at most.
| data 2        | The second data byte, where the message has one. Zero otherwise.
| data 1        | The first data byte, where the message has one. Zero otherwise.
| status        | The status byte, which says what the message is and on which channel.
|===

```c++
struct raw_message
{
   std::uint32_t data;
};
```

=== MIDI Status

The status byte indicates the type of MIDI message and includes both a status nibble (upper 4 bits) and a 16-channel number nibble (lower 4 bits).

image::midi-status.svg[alt="The two nibbles of a status byte", width=720px, align=center, title="A status byte", link={imagesdir}/midi-status.svg]

[cols="1,3"]
|===
| In the figure | What it is

| status        | Bits 7 to 4. Which message this is: a note on, a control change, a system message.
| channel       | Bits 3 to 0. Which of the sixteen channels it is for. A system message has no channel, and its status byte is whole.
|===

Here is the MIDI status enumeration:

```c++
namespace status
{
   enum
   {
      note_off         = 0x80,
      note_on          = 0x90,
      poly_pressure    = 0xA0,
      control_change   = 0xB0,
      program_change   = 0xC0,
      channel_pressure = 0xD0,
      pitch_bend       = 0xE0,
      sysex            = 0xF0,
      song_position    = 0xF2,
      song_select      = 0xF3,
      tune_request     = 0xF6,
      sysex_end        = 0xF7,
      timing_tick      = 0xF8,
      start            = 0xFA,
      continue_        = 0xFB,
      stop             = 0xFC,
      active_sensing   = 0xFE,
      reset            = 0xFF
   };
}
```

=== pitch_bend
```c++
struct pitch_bend : message3
{
   using message3::message3;

   constexpr pitch_bend(std::uint8_t channel, std::uint16_t value);
   constexpr pitch_bend(std::uint8_t channel, std::uint16_t lsb, std::uint8_t msb);

   constexpr std::uint8_t     channel() const;
   constexpr std::uint16_t    value() const;
};
```

The value is 14 bits, 0 to 16383, and the wheel at rest is 8192. The message carries the wheel position; how far full travel bends is the instrument's bend range.

=== sysex

```c++
template <int size_>
struct sysex : message<size_ + 5>
{
   constexpr sysex(std::uint16_t id, std::uint8_t const* data_in);

   constexpr std::uint16_t    id() const;
};
```

`sysex` is a system exclusive message to send, the one message with no fixed length, so it carries its own markers: 0xF0, the manufacturer's identifier, `size_` bytes of payload, then 0xF7. The identifier is written in its three byte form, a zero followed by the two halves of `id`. Payload bytes are masked to seven bits, since the eighth marks a status byte and would end the message early.

NOTE: `sysex` builds a message to send. A system exclusive message that arrives is gathered by `byte_reader`, which hands over a `sysex_view` of it. See {midi_readers}.

== Shared by Both Protocols

The controller numbers and the note numbers are the same in both protocols, so they live in `namespace midi`, in headers of their own that this one includes. See {midi_cc} and {midi_notes}.
