= MIDI Capability Inquiry

include::../../common.adoc[]

== Overview

IMPORTANT: Read {midi_readers} first for prerequisite information.

MIDI Capability Inquiry, MIDI-CI, is how two devices find out what each other can do. It is older than the Universal MIDI Packet and independent of it: the messages are universal system exclusive, they run over MIDI 1.0 as well as over MIDI 2.0, and a device is identified by a MUID, not by its connection. {midi_endpoint} covers the UMP connection; this page covers the capabilities of the device at the other end.

Everything here is in `namespace midi_ci`. Q implements version 1.2 of the specification and covers three of its categories, each with a responder for the device side and an initiator for the host side:

* Discovery: `responder` and `initiator`.
* Profile configuration: `profile_responder` and `profile_initiator`.
* Property exchange: `property_responder` and `property_initiator`.

== Chains

A device builds one chain of responders and feeds it every system exclusive message a reader produces. Each responder handles the messages of its own category and passes the rest to the next, and the discovery responder at the end sends a NAK for any other MIDI-CI message addressed to the device.

image::ci-responder-chain.svg[alt="A sysex_view passing through the property, profile and discovery responders in turn", width=750px, align=center, title="One chain. Each responder handles the messages of its category and passes the rest to the next, and the last sends a NAK for what none handled.", link={imagesdir}/ci-responder-chain.svg]

* The `sysex_view` comes from a reader.
* `property_responder` handles property exchange: Get, Set and subscriptions.
* `profile_responder` handles profiles: inquiry, on and off.
* `responder` handles Discovery and Invalidate MUID, and sends a NAK for the rest.
* Every reply goes out through `send`.

```c++
#include <q/midi/ci.hpp>
#include <q/midi/profiles.hpp>
#include <q/midi/property_exchange.hpp>
...
namespace q = cycfi::q;
namespace midi = q::midi_1_0;
namespace ci = q::midi_ci;

struct device_properties
{
   std::string_view property(std::string_view resource);
   ...
};

ci::identity id;                         // the device's identity
std::uint32_t rng();                     // a random MUID
ci::profile my_profiles[1];              // the device's profiles
device_properties my_device;             // the device's properties
midi::sysex_view msg{q::byte_span{}};    // from a reader
void send(q::byte_span reply);           // the sink
...
ci::responder discovery{id, rng};                        // innermost
ci::profile_responder profiles{my_profiles, discovery};
ci::property_responder properties{my_device, profiles};  // outermost

properties(msg, send);                                   // every sysex_view
```

The profile and property responders may be in either order. A device with no profiles leaves out the profile responder, and one with no properties leaves out the property responder. The discovery responder alone is a complete MIDI-CI device: it identifies itself and sends a NAK for every other MIDI-CI message addressed to it.

A device has one MUID, whether it sends requests or replies, so a host puts its initiators in front of the responder chain, and they use the chain's MUID. Every stage, responder or initiator, has `muid()`, which returns the discovery responder's MUID, and `announce(send)`, which sends its Discovery message.

The initiators may be chained in any order, in front of an application stage that holds the responders:

```c++
#include <q/midi/ci.hpp>
#include <q/midi/profiles.hpp>
#include <q/midi/property_exchange.hpp>
...
namespace ci = cycfi::q::midi_ci;

struct my_application { ... };           // holds the responders
my_application my_app;
...
ci::profile_initiator profile_asker{my_app};
ci::property_initiator property_asker{profile_asker};
ci::initiator inquiry{property_asker};                   // every sysex_view enters here
```

Each initiator calls its hooks on its `Next` when `Next` has them, and forwards the hooks of the other initiators, so the application stage at the end receives all of them.

== MIDI-CI Version 1.2

Three parts of version 1.2 are newer than discovery.

**Endpoint Information**, section 5.8, requests the product instance id. The id distinguishes a device's own message echoed back to it from a collision with another device of the same model, which has the same identity and a different id. `responder` replies with the id it was given, capped at the sixteen bytes the specification allows.

**The acknowledgement**, section 5.10, has the fields of the NAK and the opposite meaning. Both were given their fields in version 1.2. A version 1.1 NAK is the header alone: `message_view` reads it, and `nak_view::valid()` is false for it.

**Process inquiry**, section 9, requests the state a device holds: which controllers are where, which notes are on. A device first reports which of these it supports, and a MIDI Message Report then requests them by three bitmaps, with a control byte selecting everything or only what is not at its default.

`responder` handles Endpoint Information and Process Inquiry Capabilities, whose replies come from the device description. The reply to a MIDI Message Report is every controller and note the device holds, so a device that declares `process_feature::message_report` handles that message itself, and `responder` sends a NAK for it when the device does not declare the feature.

== What Is Not Covered

* Notify, section 8.14: `make_pe_notify` builds one, and no responder or initiator sends or handles it. The acknowledgement and the NAK replace it.
* Pagination: the header keys are declared, and paging a document is up to the device.
* Has Property Data, sub-IDs 0x32 and 0x33: the specification reserves them and gives no layout.
* The `zlib+Mcoded7` encoding: it would put a compression library into a header-only audio library for one message type.
* Profile Added and Removed reports, and profile specific data: they can be built and read, and no responder sends them, since the device decides when it gains or loses a profile.
* The initiators send property data as ASCII only, and send a Set's chunks one after the other without waiting for the per-chunk acknowledgements of flow control.
* A profile inquiry that gets a NAK ends without a call to `profiles_listed`.
* Protocol Negotiation, category 1: version 1.2 deprecated it, and the Stream Configuration Request replaced it.

For the whole list of what Q does not do, with the reason for each, see the last section of {midi}.

== Discovery

Every MIDI-CI exchange begins the same way: a device sends a Discovery message to the broadcast MUID, and every MIDI-CI device that receives it replies with its own. Each device has a MUID, a 28 bit random number it generates at power on. Profiles, property exchange and process inquiry are further exchanges built on discovery, and a device sends a NAK for a message of a category it does not support.

image::ci-discovery.svg[alt="An initiator broadcasting Discovery, a device replying, then the two version 1.2 inquiries and a NAK", width=650px, align=center, title="Discovery, then the two inquiries a responder handles on its own. Anything else addressed to it gets a NAK.", link={imagesdir}/ci-discovery.svg]

`responder` is the device side of discovery. `initiator` is the host side: it finds the MIDI-CI devices on a port and keeps a table of them as devices come and go.

The views read a message's payload, the bytes between 0xF0 and 0xF7 as a `sysex_view` gives them. `valid()` checks that the payload is the message the view names and that the fields it reads are present. The builders write into a buffer of at least `max_message` bytes.

The `Device` of the second `responder` constructor has a member `device()` that returns `device_description const&`.

=== Expressions

==== Notation

`rsp`             :: Object of type `responder<Random>`.
`ini`             :: Object of type `initiator<Next, MaxDevices>`.
`desc`            :: Object of type `device_description`.
`dev`             :: Object of a type with a member `device()` that returns `device_description const&`.
`id`              :: Object of type `identity`.
`rng`             :: Object of type `Random`, a callable that returns a random `std::uint32_t`.
`cats`            :: `std::uint8_t` value for the categories the device supports, `category` bits.
`size`            :: `std::uint32_t` value for the largest SysEx message the device takes, in bytes.
`pid`             :: `std::string_view` value for the product instance id.
`feat`            :: `std::uint8_t` value for the process inquiry features, `process_feature` bits.
`next`            :: Object of type `Next`, the next stage of the chain.
`win`             :: `std::size_t` value for the reply window, in the unit of `t`.
`t`               :: `std::size_t` value for the current time.
`msg`             :: Object of type `midi_1_0::sysex_view`.
`send`            :: A {midi_sink} over `byte_span`, or a callable that takes a `byte_span`.
`d`               :: Object of type `remote_device`.
`c`               :: `std::uint8_t` value for one `category` bit.
`m`               :: `std::uint32_t` value for a MUID.

==== Constructors

[cols="1,1"]
|===
| Expression                                     | Semantics

| `responder(desc, rng)`                         | Construct a `responder` from `desc` (device description)
                                                   and `rng` (MUID generator).
| `responder(dev, rng)`                          | Construct a `responder` from the description `dev.device()`
                                                   returns, read once.
| `responder(id, rng [, cats, size, pid, feat])` | Construct a `responder` from `id` (identity), `cats`
                                                   (categories), `size` (largest SysEx message, 512 by
                                                   default), `pid` (product instance id) and `feat`
                                                   (process inquiry features).
| `initiator(next [, win])`                      | Construct an `initiator` in front of `next`, with `win`
                                                   (reply window), three seconds in nanoseconds by default.
|===

NOTE: C++ brace initialization may also be used.

`rng` is called for a new MUID, at construction and whenever the current one is invalidated. The specification requires a good generator, and a device must not reuse a MUID across restarts. A reserved value or the broadcast MUID is drawn again.

TIP: Do not name the MUID generator `random`. POSIX declares a function of that name, so an unqualified `random` in the global namespace is ambiguous.

==== Function Call

[cols="1,1,1"]
|===
| Expression          | Semantics                                        | Return Type

| `rsp(msg, send)`    | Process `msg`, sending any reply through `send`. | `void`
| `ini(msg, send)`    | Process `msg`, then pass it to `next`, except a
                        Reply to Discovery addressed to this device.     | `void`
|===

`rsp(msg, send)` acts on these messages:

[cols="1,1"]
|===
| Message                                                        | Action

| Discovery, to all devices or to this one                       | Send a Reply to Discovery with the device description.
| Discovery from this device's own MUID                          | Send an Invalidate MUID for it, take a new MUID and
                                                                   announce it (5.9.1, option B).
| Invalidate MUID naming this device                             | Take a new MUID and announce it.
| Endpoint Information or Process Inquiry Capabilities, to this
  device                                                         | Send the reply from the device description.
| MIDI Message Report to this device, which does not declare
  `process_feature::message_report`                              | Send a NAK.
| Any MIDI-CI message to this device or to all, with reserved
  version bits set                                               | Send a NAK.
| Any other MIDI-CI message to this device                       | Send a NAK.
| Anything else                                                  | Nothing.
|===

`ini(msg, send)` acts on these messages:

[cols="1,1"]
|===
| Message                                                        | Action

| Reply to Discovery to this device                              | Add the device that sent it to the table, or refresh it.
| Reply to Discovery from this device's own MUID                 | Send an Invalidate MUID for it and pass that to `next`,
                                                                   which takes a new MUID and announces it.
| A second Reply to Discovery from one MUID in a round           | Send an Invalidate MUID for that MUID, pass that to
                                                                   `next`, and remove the device (5.9.2).
| Discovery from another device                                  | Add the device, or refresh it, and pass the message on.
| Invalidate MUID naming a device in the table                   | Remove the device, and pass the message on.
| Anything else                                                  | Pass it on.
|===

==== Operation

[cols="1,1,1"]
|===
| Expression            | Semantics                                          | Return Type

| `rsp.announce(send)`  | Send a Discovery to all devices from the current
                          MUID, as a device does at start-up.                | `void`
| `rsp.new_muid()`      | Take a new MUID from `rng`.                        | `void`
| `ini.poll(send, t)`   | Start a round at `t`, sending a Discovery, or end
                          the round once `win` has passed since its start.   | `void`
| `ini.restart()`       | Begin a new round at the next `poll`.              | `void`
| `ini.announce(send)`  | Call `next.announce(send)`.                        | `void`
|===

Q has no clock, so the caller passes the time to `poll`, in any unit; the default window is three seconds in nanoseconds, the unit of *q_io* timestamps. At the end of a round, a device that did not reply in it is removed and `complete()` becomes true. A host calls `restart()` to detect a device that has gone quiet.

==== Hooks

[cols="1,1,1"]
|===

| `next.device_removed(m)`  | Handle the removal of device `m` from the table. | `void`
|===

==== Example

A host that is also a MIDI-CI device: it replies to discovery, finds the other devices on its port and prints their MUIDs:

```c++
#include <q/midi/ci.hpp>
#include <q/midi/processor.hpp>
#include <iostream>
...
namespace q = cycfi::q;
namespace midi = q::midi_1_0;
namespace ci = q::midi_ci;

ci::identity id;                         // the device's identity
std::uint32_t rng();                     // a random MUID
void send(q::byte_span reply);           // the sink
...
struct my_host : midi::processor
{
   using midi::processor::operator();
   using discovery_type = ci::responder<std::uint32_t(*)()>;

   void poll(std::size_t now)
   {
      inquiry.poll(send, now);                           // <1>
      if (inquiry.complete())
         for (auto const& d : inquiry.devices())         // <2>
            std::cout << std::hex << d.muid << std::endl;
   }

   void operator()(midi::sysex_view msg, std::size_t time)
   {
      inquiry(msg, send);                                // <3>
   }

   discovery_type                   discovery{id, &rng}; // <4>
   ci::initiator<discovery_type&>   inquiry{discovery};  // <5>
};
```
<1> Send a Discovery at the first `poll`, and end the round once the reply window has passed.
<2> Read the table of devices found.
<3> Pass every system exclusive message to the initiator, which passes it on to the responder.
<4> Construct the discovery responder from `id` and `rng`.
<5> Construct the initiator in front of the responder, sharing its MUID.

== Profile Configuration

A profile is an agreement about what a device does with the messages it already understands. A drawbar organ profile defines which controller is which drawbar, so a control surface can drive any organ that has the profile. Q covers category 2 of MIDI-CI, from section 7 of the MIDI-CI specification and the Common Rules for MIDI-CI Profiles.

`profile_responder` is the device side: it replies from the list of profiles the device declares. `profile_initiator` is the host side: it requests a device's profiles and turns them on and off.

=== Expressions

==== Notation

`pr`              :: Object of type `profile_responder<Next, Capacity>`.
`pi`              :: Object of type `profile_initiator<Next>`.
`list`            :: Object of type `std::span<profile>`, the profiles the device declares.
`a`, `b`          :: Objects of type `profile_id`.
`addr`            :: `std::uint8_t` value for an address: a channel, `to_group` or `to_function_block`.
`n`               :: `std::uint16_t` value for a number of channels.
`on`              :: `bool` value, true when a profile is enabled.
`next`            :: Object of type `Next`, the next stage of the chain.
`msg`             :: Object of type `midi_1_0::sysex_view`.
`send`            :: A {midi_sink} over `byte_span`, or a callable that takes a `byte_span`.
`d`               :: Object of type `remote_device`.
`m`               :: `std::uint32_t` value for a MUID.

==== Constructors

[cols="1,1"]
|===
| Expression                        | Semantics

| `profile_responder(list, next)`   | Construct a `profile_responder` that replies from `list`,
                                      in front of `next`.
| `profile_initiator(next)`         | Construct a `profile_initiator` in front of `next`.
|===

NOTE: C++ brace initialization may also be used.

==== Function Call

[cols="1,1,1"]
|===
| Expression         | Semantics                                           | Return Type

| `pr(msg, send)`    | Process a profile message addressed to this device,
                       or pass `msg` to `next`.                            | `void`
| `pi(msg, send)`    | Process a profile inquiry reply or report, then
                       pass `msg` to `next`, except an inquiry reply.      | `void`
|===

`list` belongs to the caller, and `pr` writes through to it: turning a profile on or off is the one request that changes a device's state, and the application reads it as a changed `enabled` flag.

A `permanent` profile is one whose state cannot be changed; the Common Rules give the example of an acoustic piano that always conforms to the piano profile. A reply states the profile's actual state, so a request to turn a permanent profile off gets a report that it is still on.

An inquiry addressed to the function block gets one reply per address that has profiles: channels first, then the group, and the function block last, which ends the sequence.

==== Operation

[cols="1,1,1"]
|===
| Expression                           | Semantics                                     | Return Type

| `pi.ask(d, send)`                    | Send a Profile Inquiry to the function block
                                         of `d`.                                       | `void`
| `pi.turn_on(d, addr, a, send [, n])` | Send Set Profile On for `a` at `addr` of `d`,
                                         with `n` (channels to use).                   | `void`
| `pi.turn_off(d, addr, a, send)`      | Send Set Profile Off for `a` at `addr` of
                                         `d`.                                          | `void`
| `pr.announce(send)`                  | Call `next.announce(send)`.                   | `void`
| `pi.announce(send)`                  | Call `next.announce(send)`.                   | `void`
|===

==== Accessors

[cols="1,1,1"]
|===
| Expression           | Semantics                                          | Return Type

| `pr.profiles()`      | Get `list`.                                        | `std::span<profile>`
| `pr.muid()`          | Get `next.muid()`.                                 | `std::uint32_t`
| `pi.muid()`          | Get `next.muid()`.                                 | `std::uint32_t`
| `a.standard()`       | Get whether `a` is a standard profile, with 0x7E
                         in its first byte.                                 | `bool`
|===

==== Comparison

[cols="1,1,1"]
|===
| Expression           | Semantics                                          | Return Type

| `a == b`             | Equality of all five bytes.                        | `bool`
|===

==== Functions

[cols="1,1,1"]
|===
| Expression           | Semantics                                          | Return Type

| `same_profile(a, b)` | Get whether `a` and `b` are the same profile,
                         comparing their first four bytes.                  | `bool`
|===

NOTE: A request names a profile with 0x7F in its level byte, meaning as much of the profile as the device has. Use `same_profile` to match it against a declared profile: `a == b` compares all five bytes and does not match.

==== Hooks

`pi` calls these on `next` when `next` has them. `pi` keeps no table; the application keeps what a device has.

[cols="1,1,1"]
|===
| Expression                            | Semantics                                     | Return Type

| `next.profile_state(m, addr, a, on)`  | Handle the state of profile `a` at `addr` of
                                          device `m`, from a reply or a report.         | `void`
| `next.profiles_listed(m)`             | Handle the end of a profile inquiry to
                                          device `m`.                                   | `void`
|===

==== Example

A device with one profile that a host can turn on and off:

```c++
#include <q/midi/profiles.hpp>
#include <q/midi/processor.hpp>
...
namespace q = cycfi::q;
namespace midi = q::midi_1_0;
namespace ci = q::midi_ci;

ci::identity id;                         // the device's identity
std::uint32_t rng();                     // a random MUID
void send(q::byte_span reply);           // the sink
...

{
   using midi::processor::operator();
   using discovery_type = ci::responder<std::uint32_t(*)()>;

   void operator()(midi::sysex_view msg, std::size_t time)
   {
      profiles(msg, send);                                         // <1>
   }

   bool layered() const
   {
      return list[0].enabled;                                      // <2>
   }

   ci::profile list[1] = {
      {{0x7D, 0x00, 0x01, 0x02, 0x01}, ci::to_function_block}      // <3>
   };

   ci::profile_responder<discovery_type&> profiles{list, discovery}; // <5>

<1> Pass every system exclusive message to the profile responder, which passes what is not a profile message to the discovery responder.
<2> Read the profile's state, which a Set Profile On or Off changes.
<3> Declare one profile on the function block, off at start. 0x7D is the manufacturer id for non-commercial use.
<4> Construct the discovery responder, declaring the profiles category.
<5> Construct the profile responder over `list`, in front of the discovery responder.

== Property Exchange

Property Exchange reads and writes a device's properties: a resource name goes out and a JSON document comes back, or goes in. Q covers category 3, from section 8 of the MIDI-CI specification and the Common Rules for MIDI-CI Property Exchange.

`property_responder` is the device side: it serves the documents the device supplies. `property_initiator` is the host side: it reads and writes a device's properties, and subscribes to them.

}
```

`send_property` sends a document too long for one system exclusive message in chunks, with the header in the first chunk only. With flow control, a receiver takes one chunk at a time: `make_pe_ack` reports that the last chunk arrived and `make_pe_nak` requests it again. Both carry the request id and the chunk number in the five detail bytes of a MIDI-CI acknowledgement, which `pe_details_request` and `pe_details_chunk` read.

Mcoded7, from the Common Rules, carries eight bit data over a seven bit connection: each group of seven bytes becomes eight, the first carrying the top bit of each of the seven. `mcoded7_encode` and `mcoded7_decode` convert, and return zero when `out` is too small.

`header_value` reads one value from a header with no JSON parser. The Common Rules hold a header to one line with no whitespace, keys in camel case of at most twenty characters, and values that are a number, a boolean or a string.

=== Expressions

==== Notation

`pxr`             :: Object of type `property_responder<Device, Next, Capacity, SetCapacity>`.
`pxi`             :: Object of type `property_initiator<Next, Capacity, MaxRequests>`.
`dev`             :: Object of type `Device`.
`req`             :: `std::uint8_t` value for the number of requests a device takes at a time.
`next`            :: Object of type `Next`, the next stage of the chain.
`win`             :: `std::size_t` value for the reply window, in the unit of `t`.
`t`               :: `std::size_t` value for the current time.
`msg`             :: Object of type `midi_1_0::sysex_view`.
`send`            :: A {midi_sink} over `byte_span`, or a callable that takes a `byte_span`.
`d`               :: Object of type `remote_device`.
`m`               :: `std::uint32_t` value for a MUID.
`r`               :: `std::string_view` value for a resource name.
`id`              :: `std::string_view` value for a subscription id.
`cmd`             :: `std::string_view` value for a command, from `pe_command`.
`data`            :: Object of type `byte_span`, property data.
`all`             :: `bool` value, true when the MUID invalidated is this device's.
`rid`             :: `int` value for a request id.
`status`          :: `int` value for a status, from `pe_reply`.
`header`          :: `std::string_view` value for a reply header.

==== Constructors

[cols="1,1"]
|===
| Expression                               | Semantics

| `property_responder(dev, next [, req])`  | Construct a `property_responder` that serves the
                                             properties of `dev`, in front of `next`, taking `req`
                                             requests at a time (1 by default).
| `property_initiator(next [, win])`       | Construct a `property_initiator` in front of `next`,
                                             with `win` (reply window), three seconds in
                                             nanoseconds by default.
|===

NOTE: C++ brace initialization may also be used.

==== Function Call

[cols="1,1,1"]
|===
| Expression          | Semantics                                            | Return Type

| `pxr(msg, send)`    | Process a property exchange message addressed to this
                        device, or pass `msg` to `next`.                     | `void`
| `pxi(msg, send)`    | Process a reply to one of its requests or an update
                        for one of its subscriptions, or pass `msg` to
                        `next`.                                              | `void`
|===

`pxr` replies to a capabilities inquiry with `req`, and to a Get with the document `dev.property(r)` returns. A Set in chunks is gathered whole, up to `SetCapacity` bytes, before `dev.set_property` is called, and a longer one gets status 413. One Set is gathered at a time, and another that starts meanwhile gets status 343.

`pxi` gathers a reply in chunks, up to `Capacity` bytes, before calling `property_reply`. A reply too long to gather is reported with status 413, a request with no reply within `win` with `pe_reply::timed_out`, and a request the device sends a NAK for with `pe_reply::refused`. `pxi` replies to an update for one of its subscriptions with status 200. A subscription another device starts with this one goes to `next`, the responder.

==== Operation

[cols="1,1,1"]
|===
| Expression                             | Semantics                                          | Return Type

| `pxr.update(m, id, cmd, data, send)`   | Send `data` to device `m` as an update of
                                           subscription `id`, with command `cmd`, in chunks.  | `void`
| `pxi.get(d, r, send)`                  | Send `d` a Get for `r`. Return the request id, or
                                           -1 when `MaxRequests` requests are waiting.        | `int`
| `pxi.set(d, r, data, send)`            | Send `d` a Set of `r` to `data`, in chunks of at
                                           most `d.max_sysex_size` bytes. Return as `get`.    | `int`
| `pxi.subscribe(d, r, send)`            | Start a subscription to `r` on `d`. Return as
                                           `get`.                                             | `int`
| `pxi.unsubscribe(d, id, send)`         | End subscription `id` on `d`. Return as `get`.     | `int`
| `pxi.capabilities(d, send)`            | Send `d` a capabilities inquiry.                   | `void`
| `pxi.poll(t)`                          | End each request older than `win` at `t`, with
                                           `pe_reply::timed_out`.                             | `void`
| `pxr.announce(send)`                   | Call `next.announce(send)`.                        | `void`
| `pxi.announce(send)`                   | Call `next.announce(send)`.                        | `void`
|===

The device chooses `partial`, `full` or `notify` for each update; the Common Rules make it a judgement of how much changed and whether it fits one chunk.

==== Accessors

[cols="1,1,1"]
|===
| Expression           | Semantics                                          | Return Type

| `pxr.muid()`         | Get `next.muid()`.                                 | `std::uint32_t`
| `pxi.muid()`         | Get `next.muid()`.                                 | `std::uint32_t`

==== Device

`pxr` calls these on `dev`. Only `property` is required, and `pxr` detects the others.

[cols="1,1,1"]
|===
| Expression                      | Semantics                                          | Return Type

| `dev.property(r)`               | Get the document for `r`, a view into storage `dev`
                                    owns, or an empty view, which becomes a 404.       | `std::string_view`
| `dev.set_property(r, data)`     | Set `r` to `data` and return a status from
                                    `pe_reply`. Without it, a Set gets 405.            | `int`
| `dev.subscribe(m, r)`           | Start a subscription of device `m` to `r` and
                                    return its id, or an empty view, which becomes a
                                    405. Without it, a start gets 405.                 | `std::string_view`
| `dev.unsubscribe(id)`           | End subscription `id`, at either end's request.    | `void`
| `dev.muid_invalidated(m, all)`  | End the subscriptions held with device `m`, or all
                                    of them when `all` is true.                        | `void`
|===

The device holds the subscription table, so it sets how many subscribers it takes. An Invalidate MUID naming either party also ends a subscription. That message is for the discovery responder, so `pxr` passes it on and calls `muid_invalidated` as it does. When the target is this device, it has taken a new MUID and every subscription it held has ended.

NOTE: A device that supports property exchange must reply to `ResourceList` (Common Rules, 9.1). The device supplies its contents.

==== Hooks

`pxi` calls these on `next` when `next` has them.

[cols="1,1,1"]
|===
| Expression                                          | Semantics                                   | Return Type

| `next.property_reply(m, rid, status, header, data)` | Handle the reply from device `m` to request
                                                        `rid`.                                      | `void`
| `next.property_update(m, id, cmd, data)`            | Handle an update from device `m` for
                                                        subscription `id`.                          | `void`
| `next.property_capabilities(m, req)`                | Handle the number of requests device `m`
                                                        takes at a time.                            | `void`
|===

==== Example

A synth that a DAW can list programs from by name. The DAW requests `ResourceList`, finds `ProgramList` in it, requests that, and shows "Warm Pad" and "Brass" in place of program numbers.

```c++
#include <q/midi/property_exchange.hpp>
#include <q/midi/processor.hpp>
#include <string_view>
...
namespace q = cycfi::q;
namespace midi = q::midi_1_0;
namespace ci = q::midi_ci;

ci::identity id;                         // the device's identity
std::uint32_t rng();                     // a random MUID
void send(q::byte_span reply);           // the sink
...
struct my_programs
{
   std::string_view property(std::string_view resource)            // <1>
   {
      if (resource == ci::resource_list)
         return R"([{"resource":"ProgramList"}])";
      if (resource == "ProgramList")
         return R"([{"title":"Warm Pad","bankPC":[0,0,1]},{"title":"Brass","bankPC":[0,0,2]}])";
      return {};
   }
};

struct my_synth : midi::processor
{
   using midi::processor::operator();
   using discovery_type = ci::responder<std::uint32_t(*)()>;

   void operator()(midi::sysex_view msg, std::size_t time)
   {
      properties(msg, send);                                       // <2>
   }

   my_programs    programs;
   discovery_type discovery{id, &rng, ci::category::property_exchange};  // <3>
   ci::property_responder<my_programs&, discovery_type&>
                  properties{programs, discovery};                 // <4>
};
```
<1> Supply the two documents, and an empty view for any other resource, which the responder sends as a 404.
<2> Pass every system exclusive message to the property responder, which passes what is not a property exchange message to the discovery responder.
<3> Construct the discovery responder, declaring the property exchange category.
<4> Construct the property responder over `programs`, in front of the discovery responder.
