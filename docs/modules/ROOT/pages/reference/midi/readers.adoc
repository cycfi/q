= MIDI Readers

include::../../common.adoc[]

== Overview

IMPORTANT: Read {midi_processor} first for prerequisite information.

`dispatch` takes one whole message. A connection does not always hand one over.

A MIDI 1.0 byte stream can split anywhere, so a read can end in the middle of a message.

image::reader-split.svg[alt="A read boundary falling inside the second message", width=720px, align=center, title="A read ends where the buffer ends, not where a message ends.", link={imagesdir}/reader-split.svg]

MIDI 1.0 also lets a sender leave out the status byte when it repeats, so the bytes that follow do not say which message they belong to.

image::reader-running-status.svg[alt="One status byte followed by data pairs that carry none", width=720px, align=center, title="Running status: the status byte is sent once, and the pairs after it are notes on the same channel.", link={imagesdir}/reader-running-status.svg]

A system exclusive message has no fixed length at all, and on a packet connection it runs across as many packets as it needs.

image::reader-sysex.svg[alt="A system exclusive message as bytes and as packets", width=720px, align=center, title="Nothing inside a system exclusive message says how long it is. In packet form it has no markers either, and the packet status says which piece it is.", link={imagesdir}/reader-sysex.svg]

A reader sits in front of `dispatch` and makes whole messages out of what arrives. There is a reader for each protocol: `byte_reader` for MIDI 1.0 bytes, `packet_reader` for Universal MIDI Packets.

`send_sysex7` and `send_sysex8` go the other way. They take a payload and produce the packets that carry it.

Not every chain needs a reader. A device that hands over whole MIDI 1.0 messages, as q_io's {midi_stream} does, needs no `byte_reader`. A packet connection always needs `packet_reader`, since system exclusive and the text messages span packets.

See {midi} for where the readers sit among the stages.

== byte_reader

`byte_reader` takes MIDI 1.0 bytes as they come off the wire. Buffers may split anywhere, including inside a message, and the reader carries what it has across calls. It handles the three rules that make a MIDI byte stream awkward:

Running status:: A status byte holds until another replaces it, so a chord arrives as one status byte and a run of data pairs. The reader gives each pair its status.

Real time bytes:: 0xF8 and above may appear anywhere, even between the data bytes of another message or inside a system exclusive message, and leave both untouched. The reader dispatches the real time message and carries on with the one it interrupted.

System common:: Unlike real time, a system common message ends a run of running status.

A complete message goes to `dispatch`, so `proc` receives the types {midi_messages} describes. A system exclusive message is gathered from 0xF0 to 0xF7 and handed over whole, as a `sysex_view`.

```c++
#include <q/midi/byte_reader.hpp>
...
namespace midi = cycfi::q::midi_1_0;

struct my_synth : midi::processor { ... };
my_synth proc;                           // the client's processor
...
midi::byte_reader<> reader;
std::uint8_t const bytes[] = {0x90, 60, 100, 64, 100};   // two notes, one status
reader(bytes, 0, proc);   // calls proc(note_on) for key 60, then for key 64
```

=== sysex_view

```c++
struct sysex_view : message_base
{
   constexpr                  sysex_view(byte_span data);

   constexpr byte_span        data() const;
   constexpr std::uint32_t    manufacturer() const;
   constexpr bool             universal() const;
};
```

`data()` is everything between the markers, beginning with the manufacturer's identifier. The identifier is one byte, unless that byte is zero, which introduces a three byte identifier; `manufacturer()` reads either. 0x7E and 0x7F are the universal identifiers, used among other things to ask a device for its identity, and `universal()` is true for those.

NOTE: `data()` refers to the reader's own buffer and is valid only for the duration of the call. A processor that needs to keep a system exclusive message must copy it.

To build a system exclusive message to send, see xref:reference/midi/messages.adoc#_sysex[sysex] in {midi_messages}.

== packet_reader

`packet_reader` takes Universal MIDI Packets. A packet that is a message by itself goes to the MIDI 2.0 `dispatch`, so `proc` receives the types {midi2_messages} describes, and the MIDI 1.0 messages a packet may carry. What it adds is what spans packets:

System exclusive, 7 bit form:: One packet marked complete, or a start, any number of continues and an end, each carrying up to six bytes. It is handed over as the same `sysex_view` the byte reader gives, since the payload is the same.

System exclusive, 8 bit form:: The same in packets of up to thirteen bytes, every bit of every byte being data. It is handed over as a `sysex8_view`, with the stream id that distinguishes interleaved messages.

Text:: The three stream messages that carry text, an endpoint's name, its product instance id and a function block's name, are gathered the same way, into a buffer of their own, and handed over as the text views {midi_endpoint} describes. The two text banks of flex data, metadata and performance text, are gathered into a third buffer of up to 384 bytes and handed over as a `flex_text_view`. See {midi2_messages}.

Between the start and the end of a message, a system real time message or a utility message may arrive and does not affect it. Any other packet ends the message in progress, which is discarded, and that packet is read as usual.

```c++
#include <q/midi/packet_reader.hpp>
...
namespace midi2 = cycfi::q::midi_2_0;

struct my_synth : midi2::processor { ... };
my_synth proc;                           // the client's processor
extern midi2::packet pkt;                // from the connection
std::size_t time;
...
midi2::packet_reader<> reader;
reader(pkt, time, proc);
```

=== sysex8_view

```c++
struct sysex8_view : message_base
{
   constexpr                  sysex8_view(std::uint8_t stream, byte_span data);

   constexpr std::uint8_t     stream() const;
   constexpr byte_span        data() const;
};
```

A system exclusive message in its 8 bit form. Every payload byte keeps all eight of its bits, so the message cannot be sent to a MIDI 1.0 device. Like `sysex_view`, `data()` refers to the reader's buffer and is valid only for the duration of the call.

== Dropped Whole, Never Truncated

`Capacity` bounds a message. One too long for the buffer is dropped whole and counted in `drops()`, in both readers. A truncated system exclusive message is a different message from the one sent, and acting on it could mean writing the wrong patch to an instrument.

== send_sysex7

`send_sysex7` is the counterpart of the gathering in `packet_reader`: a system exclusive payload as the packets that carry it. The payload is what lies between 0xF0 and 0xF7. The markers are not sent, since the packet form has none. Six bytes go in each packet. One packet that holds the whole payload is marked complete; otherwise the first is a start, the last an end, and any between are continues.

```c++
#include <q/midi/packet_writer.hpp>
#include <vector>
...
namespace midi2 = cycfi::q::midi_2_0;

std::vector<midi2::packet> out;
...
std::uint8_t const payload[] = {0x7E, 0x7F, 0x06, 0x01};   // identity request
midi2::send_sysex7(payload, [&](midi2::packet const& p) { out.push_back(p); });
```

NOTE: Payload bytes are masked to seven bits.

== send_sysex8

`send_sysex8` is the same in its 8 bit form, and is the counterpart of the `sysex8_view` a `packet_reader` hands over. A payload byte keeps all eight of its bits, where the 7 bit form allows only seven. A message sent this way therefore cannot reach a MIDI 1.0 device, whose system exclusive carries seven bit data only. Thirteen bytes go in each packet, behind the stream id that distinguishes interleaved messages. The forms are the same: one complete packet, or a start, any number of continues, and an end.

```c++
#include <q/midi/packet_writer.hpp>
#include <vector>
...
namespace midi2 = cycfi::q::midi_2_0;

std::vector<midi2::packet> out;
...
std::uint8_t const payload[] = {0x7E, 0x00, 0xFF, 0x80};   // all eight bits
midi2::send_sysex8(
   payload, 0, [&](midi2::packet const& p) { out.push_back(p); });
```

NOTE: Nothing is masked. The count a packet declares includes the stream id, so it runs from 1 to 14 rather than 0 to 13. An empty payload still sends one packet, counting the stream id and nothing else.

== Mixed Data Sets

A mixed data set shares message type 0x5 with the 8 bit system exclusive form, and only the status distinguishes them. It carries arbitrary data, such as a firmware image or an XML document, with none of the seven bit restriction. A chunk is one header packet and as many payload packets as its size needs, and a data set is as many chunks.

`packet_reader` gathers nothing: it calls the processor with each packet as it arrives, as an `mds_header` or an `mds_payload`. A data set can run to megabytes, far past the `Capacity` that bounds a system exclusive message. The application puts the pieces back together.

```c++
namespace mds_status
{
   enum
   {
      header  = 0x8,
      payload = 0x9
   };
}

struct mds_message : packet_message\<4>
{
   using packet_message<4>::packet_message;

   constexpr std::uint8_t     mds_id() const;
};

struct mds_header : mds_message
{
   using mds_message::mds_message;

   constexpr std::uint16_t    valid_bytes() const;
   constexpr std::uint16_t    chunks() const;
   constexpr std::uint16_t    chunk() const;
   constexpr std::uint16_t    manufacturer() const;
   constexpr std::uint16_t    device() const;
   constexpr std::uint16_t    sub_id_1() const;
   constexpr std::uint16_t    sub_id_2() const;
};

struct mds_payload : mds_message
{
   using mds_message::mds_message;

   static constexpr std::size_t size = 14;

   constexpr std::uint8_t     operator[](std::size_t i) const;
};
```

`mds_id`:: Ties the parts of one data set together. Four bits, so up to sixteen data sets may be in flight in one group at once.

`valid_bytes`:: The size of this chunk in bytes, its header packet included. A chunk that is not a multiple of sixteen is padded with zeros at the end of its last payload packet.

`chunks` and `chunk`:: How many chunks the data set has, and which of them this is, numbered from one. `chunks` is zero while the sender does not know yet, as for streaming data, and the last chunk then declares the count it turned out to be.

`manufacturer`, `device`, `sub_id_1` and `sub_id_2`:: Who the data set is from, and which device should act on it. `device` is `0xFFFF` for the all call, MIDI 1.0's `0x7F`. A universal manufacturer id gives the sub ids the meaning its own specification defines; a manufacturer specific id leaves all three to that manufacturer.

A payload packet is fourteen bytes, from byte three of the packet to the end of it.

Each type is constructed from the `packet` it reads, through the constructor of `packet_message`. See {midi2_messages}.

```c++
namespace cycfi::q::midi_1_0
{
   template <std::size_t Capacity = 1024>
   class byte_reader
   {
   public:

      static constexpr std::size_t capacity = Capacity;

                              template <typename P>
                              requires concepts::midi::Processor<P>
      void                    operator()(
                                 byte_span bytes
                               , std::size_t time
                               , P&& proc
                              );

      std::size_t             drops() const;
   };
}

namespace cycfi::q::midi_2_0
{
   template <std::size_t Capacity = 1024>
   class packet_reader
   {
   public:

      static constexpr std::size_t capacity = Capacity;

                              template <typename P>
                              requires concepts::midi::Processor<P>
      void                    operator()(
                                 packet const& p
                               , std::size_t time
                               , P&& proc
                              );

      std::size_t             drops() const;
   };

   template <typename Send>

                               , Send&& send

                               , Send&& send
                               , std::uint8_t group = 0
                              );
}
```

== Expressions

=== Notation

`N`       :: A `std::size_t` value: the size of a reader's buffer, in bytes.
`R`       :: `byte_reader<N>` or `packet_reader<N>`.
`r`, `a`, `b` :: Objects of type `R`.
`br`      :: Object of type `byte_reader<N>`.
`pr`      :: Object of type `packet_reader<N>`.
`bytes`   :: A `byte_span` of MIDI 1.0 bytes, see {base}.
`pkt`     :: Object of type `midi_2_0::packet`.
`payload` :: A `byte_span`: the bytes of a system exclusive message between its markers.
`proc`    :: Instance of a type that conforms to `Processor`.
`send`    :: A {midi_sink} over `packet`, or a callable taking a `packet const&`.
`stream`  :: A `std::uint8_t` stream id, which distinguishes interleaved 8 bit messages. Zero on a device that sends one at a time.
`g`       :: A `std::uint8_t` group, 0 to 15.
`time`    :: A `std::size_t` time stamp.

=== Constructors and Assignment

[cols="1,1"]
|===
| Expression              | Semantics

| `byte_reader<>()`       | Construct a `byte_reader` whose buffer holds a system
                            exclusive message of up to 1024 bytes.
| `byte_reader<N>()`      | Construct a `byte_reader` with a buffer of `N` bytes.
| `packet_reader<>()`     | Construct a `packet_reader` whose buffer holds a
                            system exclusive message of up to 1024 bytes.
| `packet_reader<N>()`    | Construct a `packet_reader` with a buffer of `N` bytes.
| `R(r)`                  | Copy construct from `r`.
| `a = b`                 | Assign `b` to `a`.
|===

NOTE: C++ brace initialization may also be used.

=== Function Call

[cols="1,1,1"]
|===
| Expression               | Semantics                                         | Return Type

| `br(bytes, time, proc)`  | Read `bytes` and call `proc`, with `time`, for
                             each message they complete.                       | `void`
| `pr(pkt, time, proc)`    | Read `pkt` and call `proc`, with `time`, with the
                             message it holds or completes.                    | `void`
|===

=== Accessors

[cols="1,1,1"]
|===
| Expression      | Semantics                                          | Return Type

| `r.drops()`     | Get the number of messages dropped for being
                    longer than the buffer.                          | `std::size_t`
|===

=== Access

[cols="1,1,1"]
|===
| Expression      | Semantics                                          | Return Type

| `R::capacity`   | Get the size of the buffer, in bytes.              | `std::size_t`
|===

=== Functions

[cols="1,1,1"]
|===
| Expression                               | Semantics                                         | Return Type

| `send_sysex7(payload, send [, g])`       | Call `send` with each packet that carries
                                             `payload`, addressed to group `g` (0 if
                                             omitted).                                       | `void`
| `send_sysex8(payload, stream, send [, g])` | Call `send` with each 8 bit packet that
                                             carries `payload` on `stream`, addressed to
                                             group `g` (0 if omitted).                       | `void`
|===

=== Example

Read a five-pin DIN input on an STM32, where the UART interrupt calls `on_uart_byte` once per byte, at 31,250 baud, with the time `now`, and pass whole messages to a synth:

```c++
#include <q/midi/byte_reader.hpp>
...
namespace q = cycfi::q;
namespace midi = cycfi::q::midi_1_0;

struct my_synth : midi::processor { ... };
...
midi::byte_reader<> reader;                                  <1>
my_synth synth;

// Called from the UART interrupt, one byte at a time, as each lands.
void on_uart_byte(std::uint8_t byte, std::size_t now)
{
   reader(q::byte_span{&byte, 1}, now, synth);               <2>
}
```

<1> Construct a byte reader, which keeps the running status and gathers system exclusive across interrupts.
<2> Read the byte, calling `synth` with each message it completes, inside the interrupt, so the synth's overloads must be quick.
